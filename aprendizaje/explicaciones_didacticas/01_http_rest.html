HTTP y REST: el idioma entre el frontend y el backend

Cómo se arma una petición y una respuesta, qué significa cada parte y cómo se organizan las rutas de una API.

1. Problema

El frontend de Punto Lácteo corre en el navegador y está escrito en TypeScript. El backend corre en el servidor y está escrito en Python. Son dos programas separados, que no comparten memoria ni lenguaje, y a veces ni siquiera la misma máquina. Aun así, la pantalla de ventas tiene que pedirle la lista de productos al backend y entender la respuesta.

Hace falta un idioma común con tres niveles. HTTP define el «sobre», es decir, cómo se arman un pedido y una respuesta. JSON define el «contenido», o sea, cómo se escriben los datos dentro del sobre. REST es una convención para nombrar las rutas, de modo que cualquiera pueda adivinar qué hace cada una.

2. Concepto

2.1 Petición y respuesta

HTTP (HyperText Transfer Protocol o Protocolo de Transferencia de Hipertexto) funciona siempre igual: el cliente envía una petición y el servidor contesta con una respuesta. El servidor nunca habla primero. En HTTP/1.1, la versión que usa la etapa de este módulo, los dos mensajes son texto plano con cuatro partes (Figura 1 y Tabla 1).

ParteEn la peticiónEn la respuesta
Primera líneaMétodo, ruta y versión: POST /productos HTTP/1.1Versión, código y frase de estado: HTTP/1.1 201 Created
HeadersDatos sobre el pedido: a qué servidor va, en qué formato viene el cuerpo, quién pideDatos sobre la respuesta: formato, tamaño, dónde quedó lo creado
Línea en blancoMarca el fin de los headers. Todo lo que sigue es el cuerpo.
CuerpoLos datos que se envían. Es opcional: un GET no lleva.Los datos que se devuelven. Es opcional: un 204 no lleva.

2.2 HTTP no tiene memoria

HTTP es un protocolo sin estado (stateless): cada petición se entiende sola y el servidor no recuerda las anteriores. Por eso, si una ruta exige identificarse, la credencial viaja en cada petición y no solo en la primera. Ese es el papel del header Authorization de la sección 2.7.

2.4 JSON, el contenido

JSON (JavaScript Object Notation o Notación de Objetos de JavaScript) es el formato del cuerpo. Tiene seis tipos de valores: objetos {...}, listas [...], textos entre comillas dobles, números, true/false y null. En Python, json.loads convierte un texto JSON en un dict y json.dumps hace lo contrario. En JavaScript, las funciones equivalentes son JSON.parse y JSON.stringify.

¿Por qué el precio viaja entre comillas?

En JavaScript todos los números son de punto flotante, y en punto flotante 0.1 + 0.2 da 0.30000000000000004. Con dinero, ese error se acumula venta tras venta. Por eso el precio viaja como texto ("12500.00") y cada lado lo convierte a un tipo decimal exacto, que en Python es Decimal. FastAPI hace lo mismo con los campos de tipo Decimal. Además, JSON usa siempre punto decimal: la coma de «0,350 kg» es solo para mostrar en pantalla.

2.5 REST: cómo se nombran las rutas

REST (Representational State Transfer o Transferencia de Estado Representacional) es un estilo para diseñar APIs sobre HTTP. La URL nombra una cosa, llamada recurso (por ejemplo, un producto), y el método dice qué se hace con ella. Las URL llevan sustantivos y los métodos son los verbos (Tabla 3).

MétodoQué haceEjemplo en Punto Lácteo¿Seguro?¿Idempotente?Respuesta típica
GETLeeGET /productos (todos)
GET /productos/1 (uno)		SíSí200 OK
POSTCreaPOST /productosNoNo201 Created
PUTReemplaza completoPUT /productos/1NoSí200 OK
PATCHModifica una partePATCH /productos/1 con {"precio": "13000.00"}NoNo necesariamente200 OK
DELETEBorraDELETE /productos/1NoSí204 No Content

Un método es seguro si no modifica datos, así que se puede llamar sin miedo. Es idempotente si repetirlo varias veces deja el mismo estado que hacerlo una vez. La diferencia importa cuando falla la red. Si la cajera toca «Cobrar», la conexión se corta y no llega la respuesta, reintentar un DELETE es inofensivo, pero reintentar un POST puede registrar la venta dos veces.

Sin una convención, cada API inventa sus nombres: /crearProducto, /borrarProducto?id=7, /obtenerTodosLosProductos. Con REST, las mismas acciones son POST /productos, DELETE /productos/7 y GET /productos. Los filtros van como parámetros de consulta (query parameters) después del signo ?, por ejemplo GET /ventas?fecha=2026-10-30.

2.6 Códigos de estado

El código de estado es un número de tres cifras que resume el resultado. La primera cifra indica la familia: 2xx significa que salió bien, 3xx que hay que ir a otra dirección, 4xx que el error es de quien pidió y 5xx que el error es del servidor (Tabla 4).

2.7 Primera mirada al token Bearer

Para borrar un producto, la etapa 01 exige el header Authorization: Bearer token-de-prueba-123. Bearer significa «portador»: el servidor deja pasar a quien porte el token, sin preguntar nada más. Funciona como la entrada de un recital, donde quien la tiene, entra. Por eso el token se cuida como una contraseña.

En esta etapa el token es un texto fijo escrito en el código, solo para ver cómo viaja. Además, todo viaja sin cifrar, y por eso se puede leer en la terminal. En producción se usa HTTPS (HTTP Secure o HTTP Seguro), que cifra el mensaje completo. En el módulo 06 el token fijo se reemplaza por un JWT (JSON Web Token o Token Web JSON), que el servidor genera al iniciar sesión, firma y hace vencer.

3. Código mínimo

El código está en aprendizaje/etapas/01_http. El servidor usa http.server, el módulo de la biblioteca estándar de Python para servidores HTTP básicos. No se usa FastAPI a propósito: así queda a la vista todo el trabajo que un framework hace por detrás.

Python mira el método de la primera línea y llama a do_GET, do_POST o do_DELETE. Dentro de cada uno, la ruta se separa a mano:

def do_GET(self):
    self._registrar_peticion()

    if self.path == "/productos":
        return self._responder(HTTPStatus.OK, list(productos.values()))

    coincidencia = RUTA_PRODUCTO.match(self.path)      # /productos/<número>
    if coincidencia:
        producto = productos.get(int(coincidencia.group(1)))
        if producto is None:
            return self._responder(HTTPStatus.NOT_FOUND, {"detail": "Producto no encontrado"})
        return self._responder(HTTPStatus.OK, producto)

    self._responder(HTTPStatus.NOT_FOUND, {"detail": "Ruta no encontrada"})

Para crear, el cuerpo se convierte de texto JSON a dict y se valida campo por campo:

try:
    datos = json.loads(self.cuerpo)
except json.JSONDecodeError:
    return self._responder(HTTPStatus.BAD_REQUEST, {"detail": "El cuerpo no es JSON válido"})

errores = validar_producto(datos)
if errores:
    return self._responder(HTTPStatus.BAD_REQUEST, {"detail": errores})

Cada respuesta se arma en el mismo orden que la Tabla 1: línea de estado, headers, línea en blanco y cuerpo:

self.send_response(codigo)                                   # línea de estado
self.send_header("Content-Type", "application/json; charset=utf-8")
self.send_header("Content-Length", str(len(cuerpo)))
self.end_headers()                                           # línea en blanco
self.wfile.write(cuerpo)                                     # cuerpo

Se ejecuta con dos terminales abiertas en la carpeta de la etapa. El README.md de la etapa explica también cómo probar con el navegador y con curl.exe.

python servidor.py      # terminal 1: queda esperando peticiones
python cliente.py       # terminal 2: envía los casos de a uno

6. Errores comunes

Usar GET para acciones que modifican datos.

Una ruta como GET /productos/2/borrar rompe la promesa de que GET es seguro. Los navegadores y otras herramientas pueden repetir o precargar peticiones GET por su cuenta, y un simple enlace terminaría borrando productos.

Responder 200 a todo y poner el error en el cuerpo.

Con 200 {"ok": false}, el cliente tiene que leer el texto para saber si algo falló. Los códigos de estado existen justamente para eso, y todas las herramientas (el navegador, fetch, los registros del servidor) los entienden.

Confundir 401 con 403.

401 significa que el servidor no sabe quién pide. 403 significa que lo sabe y esa persona no tiene permiso. Un empleado identificado que intenta anular una venta recibe 403.

Escribir decimales con coma dentro del JSON.

{"precio": 12500,50} no es JSON válido: la coma separa elementos. El servidor de la etapa responde 400 con «El cuerpo no es JSON válido».

Usar verbos en las rutas.

/crearProducto o /borrarProducto repiten en la URL lo que ya dice el método. En REST la ruta es el recurso y el método es la acción.

Escribir curl en lugar de curl.exe en Windows PowerShell.

En Windows PowerShell, curl es un alias de Invoke-WebRequest, que usa otras opciones. curl.exe ejecuta el curl real que viene con Windows.

7. Ejercicios

1. Ejecutá cliente.py dos veces sin reiniciar el servidor. ¿Qué cambia en el caso 6 la segunda vez? ¿Sigue siendo DELETE idempotente?

Ver respuesta

La segunda vez el caso 6 responde 404, porque el producto 2 ya se borró. La respuesta cambia, pero el estado final es el mismo: el producto 2 no existe. La idempotencia se refiere al estado del servidor, no al código de respuesta.

2. Implementá PATCH /productos/{id} para cambiar solo el precio de un producto. ¿Qué código devolvés si el producto no existe? ¿Y si el precio no es válido? ¿Debería pedir token?

Ver respuesta

Se agrega un método do_PATCH. Responde 404 si el producto no existe, 400 si el precio no es válido y 200 con el producto actualizado si salió bien. Como modifica datos, conviene exigir el mismo token que DELETE. Un esqueleto posible:

def do_PATCH(self):
    self._registrar_peticion()
    coincidencia = RUTA_PRODUCTO.match(self.path)
    # 1. ¿la ruta es /productos/<n>?  → si no, 404
    # 2. ¿trae Authorization: Bearer ...?  → si no, 401
    # 3. ¿existe el producto?  → si no, 404
    # 4. ¿el precio es un Decimal mayor que cero?  → si no, 400
    # 5. actualizar y responder 200 con el producto

3. Sin ejecutar nada, ¿qué código de estado corresponde a cada caso? (a) La dueña pide /ventas?fecha=2026-13-45. (b) Un empleado con un token válido intenta borrar un producto y no tiene permiso. (c) Se intenta vender más queso del que hay. (d) El backend intenta conectarse a la base de datos y está apagada.

Ver respuesta

(a) 400, porque la fecha no es válida; FastAPI respondería 422. (b) 403, porque se sabe quién pide pero no tiene permiso. (c) 409, porque el pedido choca con el stock actual. (d) 500 (o 503, Service Unavailable), porque el error es del servidor y no de quien pidió.

4. Creá el archivo ejemplos/roto.json con el texto {"nombre": "Queso" (sin cerrar la llave) y envialo con curl.exe. ¿Qué responde el servidor y qué línea de servidor.py lo decide?

Ver respuesta

Responde 400 con {"detail": "El cuerpo no es JSON válido"}. Lo decide el bloque except json.JSONDecodeError de do_POST: json.loads no puede convertir el texto y lanza esa excepción.

5. Abrí http://127.0.0.1:8000/productos en el navegador con el servidor levantado y mirá su terminal. ¿Qué headers manda el navegador que cliente.py no manda? ¿Aparece alguna petición que no pediste?

Ver respuesta

El navegador agrega, entre otros, User-Agent (qué navegador es), Accept-Language (idiomas preferidos) y un Accept con varios formatos. Además, suele pedir por su cuenta GET /favicon.ico, el ícono de la pestaña, que el servidor responde con 404 «Ruta no encontrada».
