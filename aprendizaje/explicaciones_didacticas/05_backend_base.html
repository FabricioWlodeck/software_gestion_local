Backend ↔ base de datos: SQLAlchemy, transacciones y migraciones

Cómo el backend lee y escribe en MariaDB, qué hace el ORM por debajo, cómo una transacción evita datos a medias y cómo se versiona el esquema con Alembic.

1. Problema

La etapa 03 tiene las reglas del negocio bien separadas, pero los datos viven en memoria. La etapa 04 tiene una base de datos bien diseñada, pero nadie la usa. Este módulo las une, y al hacerlo aparecen tres problemas que en memoria no existían.

El primero es que una venta implica varias escrituras (la cabecera, las líneas y el stock de cada producto), y si el servidor se cae en el medio no puede quedar la mitad guardada. El segundo es que dos cajas pueden vender el mismo queso al mismo tiempo, y con una base compartida eso es real: en la etapa 05, si no se hace nada, se venden 3 kg de un queso del que había 2,1 kg. El tercero es que el esquema de la base va a cambiar durante el proyecto (el módulo 06 agrega contraseñas), y esos cambios tienen que aplicarse igual en la PC de desarrollo y en el servidor.

2. Concepto

2.1 Controlador y ORM

Para hablar con MariaDB, Python necesita un controlador (driver): una librería que conoce el protocolo de red del motor. La etapa usa PyMySQL. Con el controlador solo, el código escribe SQL como texto y recibe tuplas.

Encima del controlador se usa un ORM (Object-Relational Mapper o Mapeador Objeto-Relacional): SQLAlchemy. El ORM permite declarar cada tabla como una clase y cada fila como un objeto, y escribe el SQL por su cuenta. Una venta deja de ser «un INSERT en venta y otro en venta_detalle» y pasa a ser un objeto Venta con una lista de detalles. El SQL no desaparece: el ORM lo genera, y la etapa lo muestra en la terminal para que se vea.

2.2 Engine y URL de conexión

El engine sabe a qué base conectarse y mantiene un pool de conexiones abiertas para reutilizarlas, porque abrir una conexión nueva en cada petición es lento. Se configura con una URL de la forma dialecto+controlador://usuario:contraseña@servidor:puerto/base: 

mariadb+pymysql://pl:pl123@127.0.0.1:3307/punto_lacteo_orm?charset=utf8mb4

Cambiar de motor es cambiar ese texto: sqlite:///./punto_lacteo.db usa SQLite y postgresql+psycopg://... usa PostgreSQL. Funciona porque el código usa tipos genéricos (Numeric, String) y SQLAlchemy traduce cada consulta al dialecto de cada motor.

2.3 Modelos y schemas: dos clases para dos trabajos

Un modelo (app/models.py) describe una tabla: columnas, claves y relaciones. Un schema (app/schemas/) describe lo que entra y sale por HTTP. Se parecen, pero no son lo mismo: el modelo Usuario del módulo 06 tendrá el hash de la contraseña y el schema de salida no, y VentaIn no tiene id porque lo asigna la base. Con model_config = ConfigDict(from_attributes=True), Pydantic arma un schema leyendo los atributos de un objeto ORM: VentaOut.model_validate(venta).

En el modelo, Mapped[Decimal] indica el tipo de Python y mapped_column(Numeric(10, 3)) el tipo de la columna. relationship() no crea columnas: permite navegar entre objetos, como venta.detalles o detalle.producto.

2.4 La sesión

La sesión es la conversación con la base durante una petición. Cada petición recibe una sesión nueva mediante la dependencia obtener_sesion. La sesión hace tres trabajos. Primero, abre una transacción con la primera consulta (en el registro aparece BEGIN (implicit)). Segundo, recuerda los objetos que cargó y detecta los cambios: producto.stock -= cantidad no envía nada, solo marca el objeto como modificado. Tercero, envía todos los cambios pendientes juntos cuando se llama a flush(), o a commit(), que hace un flush() y confirma.

flush() envía el SQL, pero sin confirmar: los cambios todavía se pueden deshacer. Se usa cuando hace falta un dato que asigna la base, como el id de la venta nueva. commit() confirma, y recién ahí los cambios quedan guardados y visibles para las demás conexiones.

2.5 Transacciones

Una transacción es un grupo de operaciones que la base trata como una sola. Garantiza cuatro propiedades, conocidas como ACID (Atomicity, Consistency, Isolation, Durability o Atomicidad, Consistencia, Aislamiento y Durabilidad). Con la atomicidad se aplican todas las operaciones o ninguna. Con la consistencia, la base pasa de un estado válido a otro, respetando las restricciones. Con el aislamiento, las transacciones simultáneas no ven los cambios a medio hacer de las otras. Con la durabilidad, lo confirmado sobrevive a un corte de luz.

En ServicioVentas.registrar, todo lo que pasa entre el primer SELECT y el commit() es una transacción. Si una regla falla, el service lanza un error, la sesión se cierra sin confirmar y MariaDB hace ROLLBACK: descarta todo lo enviado. En el registro del servidor se ve cada venta rechazada terminar así.

2.6 Concurrencia: dos cajas, un queso

Dos cajas pueden leer el mismo stock antes de que alguna lo modifique. Si las dos leen 2,1 kg, las dos aprueban una venta de 1,5 kg y las dos guardan «2,1 − 1,5 = 0,6». El stock termina en 0,6 kg y se vendieron 3 kg. Este error se llama actualización perdida (lost update), y ninguna restricción CHECK lo detecta, porque 0,6 es un valor válido.

La solución es SELECT ... FOR UPDATE: al leer el producto, la transacción bloquea su fila hasta el commit. La segunda caja que pide la misma fila espera, y cuando la primera confirma, lee el stock ya actualizado. En SQLAlchemy se escribe .with_for_update(). El service bloquea los productos en orden de id: si una venta bloqueara queso y después leche y otra leche y después queso, cada una podría quedar esperando a la otra para siempre, situación conocida como interbloqueo (deadlock). demo_concurrencia.py reproduce los dos casos.

2.7 ¿Quién hace el commit?

Un patrón común es confirmar en la dependencia, después del yield. En la versión de FastAPI que usa la etapa, ese código se ejecuta después de enviar la respuesta. Si el commit fallara ahí, el cliente ya habría recibido un 201 por una venta que no se guardó. Por eso, en la etapa, cada service llama a self.sesion.commit() antes de devolver, y la dependencia solo cierra la sesión. El service es además quien sabe cuándo una operación está completa.

2.8 Consultas con el ORM

sesion.get(Producto, 1) busca por clave primaria. select(Producto).where(...) arma una consulta, y sesion.scalars(consulta) la ejecuta y devuelve objetos. Para listar ventas con sus líneas se usa selectinload, que trae todas las líneas en una consulta extra. Sin eso, el ORM haría una consulta por cada venta al leer venta.detalles, un problema conocido como «N+1 consultas».

2.9 Migraciones con Alembic

Una migración es un archivo que describe un cambio del esquema (crear una tabla, agregar una columna) y cómo deshacerlo. Alembic guarda en la base, en la tabla alembic_version, cuál fue la última migración aplicada, y alembic upgrade head aplica las que falten. Es el equivalente de git para el esquema: la PC de desarrollo y el servidor llegan al mismo esquema ejecutando las mismas migraciones en el mismo orden.

alembic revision --autogenerate compara los modelos con la base y escribe la migración. La primera migración de la etapa (0001_esquema_inicial.py) se generó así y crea las mismas cuatro tablas que el SQL escrito a mano en el módulo 04. La generación automática no es infalible (no detecta, por ejemplo, un cambio de nombre de columna), y por eso cada migración se lee antes de aplicarla.

3. Código mínimo

Un modelo con sus columnas, restricciones y relaciones:

class Venta(Base):
    __tablename__ = "venta"

    id: Mapped[int] = mapped_column(primary_key=True)
    fecha: Mapped[datetime] = mapped_column(server_default=func.current_timestamp(), index=True)
    usuario_id: Mapped[int] = mapped_column(ForeignKey("usuario.id"))
    total: Mapped[Decimal] = mapped_column(Numeric(12, 2))

    detalles: Mapped[list["VentaDetalle"]] = relationship(back_populates="venta", cascade="all, delete-orphan")

Una sesión por petición, entregada por una dependencia:

engine = create_engine(DATABASE_URL, echo=MOSTRAR_SQL, pool_pre_ping=True)
SesionLocal = sessionmaker(bind=engine, expire_on_commit=False)

def obtener_sesion() -> Iterator[Session]:
    with SesionLocal() as sesion:   # al salir, se cierra; lo no confirmado se descarta
        yield sesion

La lectura con bloqueo y el commit en el service:

consulta = select(Producto).where(Producto.id == producto_id).with_for_update()
producto = self.sesion.scalars(consulta).first()
...
self.sesion.commit()

Preparación y ejecución, desde la carpeta de la etapa (el README.md tiene el paso a paso completo):

alembic upgrade head          # crea las tablas con las migraciones
python -m app.semilla         # carga usuarios y productos
fastapi dev app/main.py       # la API, mostrando cada consulta SQL
python demo_concurrencia.py   # la carrera entre dos cajas

4. Cómo se conecta

La predicción de la Tabla 2 del módulo 03 se cumplió: para pasar de memoria a MariaDB cambiaron los repositorios y las dependencias, y los routers quedaron idénticos (Tabla 1).

Queda un problema a la vista: VentaIn trae un usuario_id, así que la caja dice quién cobra y el servidor le cree. Cualquiera podría registrar ventas a nombre de otra persona. El módulo 06 lo resuelve tomando el usuario del token de sesión, y su migración agrega las columnas de contraseña y rol.

6. Errores comunes

Olvidar el commit().

La API responde 201, la venta aparece mientras dura la petición, y al cerrarse la sesión todo se descarta. En el registro del servidor, la transacción termina en ROLLBACK en lugar de COMMIT.

Leer y después escribir sin bloqueo.

Es el error de la actualización perdida: funciona en todas las pruebas con un solo usuario y falla el primer sábado con dos cajas abiertas. Toda lectura que decide una escritura sobre la misma fila va con with_for_update().

Devolver objetos ORM después de cerrar la sesión.

Si una relación no se cargó, acceder a ella con la sesión cerrada lanza DetachedInstanceError. La etapa convierte todo a schemas dentro del service, con la sesión abierta.

Aplicar una migración autogenerada sin leerla.

Si se renombra una columna en el modelo, la generación automática propone borrar la columna vieja y crear una nueva, y eso borra los datos. Siempre se revisa el archivo antes de alembic upgrade.

Escribir la contraseña de la base en el código.

La etapa tiene un valor por defecto para aprender, pero DATABASE_URL se lee de una variable de entorno. En el servidor, la contraseña real va en un archivo .env que no se sube a git (módulo 10).

Ignorar la zona horaria.

MariaDB, dentro del contenedor, usa UTC. Una venta de las 23:30 hora local queda registrada al día siguiente, y el resumen «de hoy» sale mal. Lo habitual es guardar en UTC y convertir a la hora local al mostrar o al filtrar.

7. Ejercicios

1. Comentá la línea self.sesion.commit() de registrar, registrá una venta y después listá las ventas. ¿Qué responde cada petición y qué muestra el registro del servidor?

Ver respuesta

La venta responde 201 con un id, pero el listado no la muestra y el stock no cambió. El registro muestra los INSERT y el UPDATE (por el flush) seguidos de ROLLBACK: la sesión se cerró sin confirmar. Es el motivo por el que el commit es explícito.

2. En demo_concurrencia.py, ¿qué pasa si se cambia time.sleep(1.0) por time.sleep(0) en la prueba sin bloqueo? ¿El problema desaparece?

Ver respuesta

Probablemente la segunda caja lea el stock después del commit de la primera y el resultado salga bien. El problema no desaparece: solo se vuelve menos probable y más difícil de reproducir. Los errores de concurrencia dependen del momento exacto, y por eso se previenen con bloqueos en lugar de confiar en que «no pasa».

3. Cambiá la base a SQLite sin tocar el código: en una terminal nueva ejecutá $env:DATABASE_URL = "sqlite:///./punto_lacteo.db", después alembic upgrade head, python -m app.semilla y fastapi dev app/main.py. ¿Funciona la venta? ¿Qué pasa con el FOR UPDATE?

Ver respuesta

Funciona: se crea el archivo punto_lacteo.db con las mismas tablas. SQLite no tiene bloqueo por fila, así que SQLAlchemy omite FOR UPDATE; SQLite bloquea la base entera mientras alguien escribe. Para un solo puesto de venta alcanza; para varias cajas a la vez, un motor servidor como MariaDB o PostgreSQL es más adecuado.

4. Agregá al modelo Producto una columna stock_minimo: Mapped[Decimal] = mapped_column(Numeric(10, 3), default=Decimal("0"), server_default="0"), generá la migración con alembic revision --autogenerate -m "stock minimo" y leela antes de aplicarla. ¿Por qué hace falta server_default?

Ver respuesta

La migración tiene un op.add_column en upgrade y un op.drop_column en downgrade. server_default hace falta porque la tabla ya tiene filas: sin un valor por defecto en la base, MariaDB no puede agregar una columna NOT NULL a filas existentes. default solo lo usa Python al crear objetos nuevos.

5. Escribí en el repositorio de ventas un método que devuelva el total vendido entre dos fechas, usando func.sum. Es la consulta que necesitará el resumen semanal del bot.

Ver respuesta 
from sqlalchemy import func

def total_entre(self, desde: datetime, hasta: datetime) -> Decimal:
    consulta = select(func.coalesce(func.sum(Venta.total), 0)).where(Venta.fecha >= desde, Venta.fecha < hasta)
    return self.sesion.scalar(consulta)
