Mapa general: el viaje de una venta

Qué piezas tiene un sistema web, qué hace cada una y por dónde pasa una venta desde el clic hasta la base de datos.

1. Problema

Una cajera de Punto Lácteo pesa 0,350 kg de queso cremoso, carga el peso en la pantalla y toca Cobrar. En una fracción de segundo, el sistema tiene que calcular el total, guardar la venta y descontar el stock. Para que eso pase intervienen varios programas, que pueden estar en máquinas distintas y están escritos en lenguajes distintos.

Este módulo dibuja el mapa de esas piezas. Los módulos siguientes estudian cada pieza por separado, y el mapa sirve para no perder de vista dónde encaja cada una. Este módulo no tiene código para ejecutar.

2. Concepto

Un sistema web se divide en piezas que tienen una sola responsabilidad cada una. La división más común, y la que usa este proyecto, separa la interfaz, la lógica y los datos (Tabla 1). La pieza central es la API (Application Programming Interface o Interfaz de Programación de Aplicaciones), que es el conjunto de rutas que el backend ofrece para que otros programas le pidan cosas. La base de datos se consulta con SQL (Structured Query Language o Lenguaje de Consulta Estructurado).

Por qué se divide en piezas

La primera razón es que cada pieza se puede cambiar sin tocar las otras, siempre que respete lo que las demás esperan de ella. Si el sistema migra de MariaDB a PostgreSQL, cambia la capa de acceso a datos y la pantalla de ventas no se entera.

La segunda razón es que cada pieza se entiende y se prueba por separado. Un total mal calculado se busca en el backend, sin revisar el código de las pantallas.

La tercera razón es la seguridad, que depende de dónde se ejecuta cada cosa. El navegador está en manos del usuario: cualquiera puede abrir las herramientas de desarrollo y modificar el código que corre ahí, o enviarle peticiones a la API sin pasar por la pantalla. Por eso las reglas del negocio («no se vende más stock del que hay», «un empleado no anula ventas») se aplican en el backend, que es el único lugar que el usuario no controla.

Regla de oro. El backend no confía en nada de lo que llega del frontend. El frontend puede validar para dar una mejor experiencia, pero el backend vuelve a validar siempre.

Las capas dentro del backend

El backend también se divide. El router recibe la petición y, con ayuda de Pydantic, comprueba que los datos tengan la forma correcta. El service aplica las reglas del negocio y decide. La capa de acceso a datos habla con la base. Cada capa solo llama a la de abajo. El módulo 03 explica qué se gana con esta división y qué se pierde si se mezcla todo en un solo archivo.

3. Código mínimo

Este módulo no tiene código para ejecutar. Los fragmentos siguientes son una vista previa simplificada de cómo se ve cada pieza. No hace falta entenderlos ahora; el objetivo es reconocerlos cuando aparezcan en su módulo.

En el frontend (módulos 08 y 09), React envía la venta al backend con fetch:

async function cobrar() {
  const respuesta = await fetch("/ventas", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ producto_id: 1, cantidad: "0.350" }),
  });
}

En el backend (módulos 02 y 03), FastAPI asocia la ruta con una función y Pydantic define la forma de los datos:

class VentaIn(BaseModel):
    producto_id: int
    cantidad: Decimal = Field(gt=0)   # gt = greater than (mayor que)

@router.post("/ventas", status_code=201)
def crear_venta(venta: VentaIn, servicio: VentaService = Depends()):
    return servicio.registrar(venta)

En el service (módulo 03) viven las reglas del negocio:

def registrar(self, venta: VentaIn):
    producto = self.repositorio.obtener_para_actualizar(venta.producto_id)
    if producto.stock < venta.cantidad:
        raise StockInsuficiente(disponible=producto.stock)
    ...

En la base de datos (módulos 04 y 05), SQLAlchemy termina enviando SQL como este:

START TRANSACTION;
SELECT stock FROM producto WHERE id = 1 FOR UPDATE;
INSERT INTO venta (producto_id, cantidad, total) VALUES (1, 0.350, 4375.00);
UPDATE producto SET stock = stock - 0.350 WHERE id = 1;
COMMIT;

4. Cómo se conecta

Dos piezas se conectan a través de un contrato: un acuerdo sobre qué se envía, con qué formato y qué se responde. Mientras el contrato se respete, cada lado puede cambiar por dentro sin romper al otro (Tabla 2).

ConexiónCómo se comunicanQué fija el contrato
Frontend → backendPeticiones HTTP con cuerpo JSONLas rutas (POST /ventas), los nombres de los campos y los códigos de respuesta
Router → serviceLlamadas a funciones de PythonQué datos recibe el service y qué errores puede lanzar
Service → acceso a datosLlamadas a funciones de PythonQué operaciones se ofrecen (obtener un producto, guardar una venta)
Acceso a datos → baseConsultas SQL por una conexión de red al puerto 3306La cadena de conexión (usuario, contraseña, servidor, base) y el esquema de tablas

El navegador nunca se conecta directamente con la base de datos. Si lo hiciera, la contraseña de la base tendría que estar en el código del frontend, y cualquiera que abriera la página podría leerla. El backend es el único intermediario autorizado.

6. Errores comunes

Validar el stock solo en React.

Quien conozca la ruta puede enviar la petición con curl o desde las herramientas del navegador y saltear la pantalla. La validación del frontend mejora la experiencia, pero la que protege los datos es la del backend.

Pensar que el frontend y el backend son el mismo programa.

Son dos procesos distintos, que pueden ejecutarse en máquinas distintas. Por eso se comunican por HTTP y no llamándose funciones entre sí.

Confundir «el servidor» máquina con «el servidor» programa.

La máquina de la facultad es un servidor físico o virtual. FastAPI es un programa servidor que corre en esa máquina, igual que MariaDB. En una misma máquina pueden correr varios programas servidores, cada uno en su puerto.

Poner reglas del negocio en el router.

Si la regla de stock vive en la función del router, no se puede reutilizar desde otro lugar (por ejemplo, desde un futuro bot) sin copiarla. El router traduce HTTP; el service decide.

7. Ejercicios

1. La dueña quiere ver las ventas de hoy. Recorré el mapa: ¿qué tipo de pedido hace el frontend, qué capas atraviesa y hace falta una transacción que escriba datos?

Ver respuesta

El frontend hace un pedido de lectura (GET /ventas?fecha=hoy, se ve en el módulo 01). Pasa por el router, que valida los parámetros; por el service, que además debería verificar que quien pide sea la dueña (módulo 06); y por el acceso a datos, que ejecuta un SELECT. No se modifica ningún dato, así que no hace falta una transacción de escritura. La respuesta es un 200 con la lista de ventas en JSON.

2. ¿En qué capa va la regla «un empleado no puede anular una venta»? ¿Por qué no alcanza con ocultar el botón Anular en la pantalla de los empleados?

Ver respuesta

Va en el backend, en el service o en una dependencia de permisos (módulo 06). Ocultar el botón es buena experiencia de uso, pero cualquiera puede enviar la petición HTTP directamente. El backend tiene que rechazarla con un código 403 (prohibido) aunque la pantalla nunca muestre el botón.

3. Si el sistema migra de MariaDB a PostgreSQL, ¿qué piezas del mapa cambian y cuáles no?

Ver respuesta

Cambia la base de datos y, en la capa de acceso a datos, la cadena de conexión y el controlador. Si se usaron funciones propias de MariaDB, también esas consultas. El router, el service y el frontend no cambian, porque sus contratos siguen siendo los mismos. Esa es la ganancia de separar en capas.

4. En el escenario sin stock, ¿por qué el service consulta el stock en la base en lugar de usar el que muestra la pantalla de la cajera?

Ver respuesta

Porque el dato de la pantalla puede estar desactualizado: otra caja, o el otro local, pudo vender queso después de que la pantalla se cargó. Además, el frontend no es confiable. La única fuente de verdad en ese instante es la base de datos.
