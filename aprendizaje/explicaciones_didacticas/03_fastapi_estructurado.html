FastAPI estructurado: una carpeta por responsabilidad

Cómo se divide el backend en routers, schemas, services y repositories, qué aporta cada capa y cómo las conecta FastAPI con Depends.

1. Problema

El main.py de la etapa 02 tiene productos. El sistema real va a tener ventas, stock, proveedores, usuarios, reportes y un bot de Telegram. Si todo sigue en un archivo, aparecen cuatro problemas concretos.

  1. La regla «no se vende sin stock» queda dentro de una ruta HTTP, y el bot no la puede usar sin copiarla.
  2. Pasar de memoria a MariaDB obliga a tocar todas las rutas, porque cada una accede al diccionario.
  3. Probar una regla exige levantar el servidor y enviar peticiones HTTP.
  4. Dos personas que editan el mismo archivo enorme chocan en cada cambio de git.

La etapa 03 reorganiza el código en capas y agrega las ventas, con control de stock. Los datos siguen en memoria, a propósito: en el módulo 05 se pasan a MariaDB cambiando una sola capa.

2. Concepto

2.1 Una capa, una pregunta

La idea central se llama separación de responsabilidades: cada archivo responde una sola pregunta y no se mete en las de los demás (Tabla 1). Así, cuando algo cambia, se sabe qué archivo tocar y cuáles quedan intactos.

CapaDóndePregunta que respondeQué no hace
Routerrouters/¿Qué ruta HTTP es y qué se devuelve?No decide reglas ni accede a los datos
Schemaschemas/¿Qué forma tienen los datos que entran y salen?No consulta datos ni conoce reglas
Serviceservices/¿Esto se puede hacer según las reglas del negocio?No sabe de HTTP ni de cómo se guardan los datos
Repositoryrepositories/¿Cómo se guardan y se buscan los datos?No valida reglas del negocio
Erroreserrores.py¿Qué puede salir mal en el negocio?No eligen el código HTTP
Dependenciasdependencies.py¿Cómo se construye cada pieza?No atienden rutas
Entradamain.py¿Qué piezas forman la aplicación?No tiene rutas ni reglas propias

2.2 Las dependencias van en una sola dirección

Los routers importan services, los services importan repositories, y nunca al revés. Ningún service importa nada de FastAPI. Esa regla es la que permite reutilizar el service desde un script o un bot: el archivo probar_service.py registra ventas sin servidor, sin HTTP y sin FastAPI. 

routers/   ──usa──▶   services/   ──usa──▶   repositories/
   │                     │                        │
   └────────── todos usan schemas/ ───────────────┘
                         │
                 lanza errores.py  ──▶  main.py los traduce a HTTP

2.3 Inyección de dependencias con Depends

Una ruta necesita un ServicioVentas, que a su vez necesita dos repositorios. En lugar de construirlos adentro de la ruta, la ruta los declara en su firma: servicio: ServicioVentasDep. Antes de ejecutar la ruta, FastAPI llama a la función indicada en Depends(...) y le pasa el resultado. Este patrón se llama inyección de dependencias: la pieza recibe lo que necesita desde afuera en lugar de fabricarlo.

La ganancia es que la forma de construir el service vive en un solo lugar. En el módulo 05, dependencies.py pasa a crear repositorios con una conexión a MariaDB, y ninguna ruta cambia. Las dependencias también sirven como guardias: exigir_token se agrega a cualquier ruta con dependencies=[Depends(exigir_token)] y corta la petición con 401 antes de que la ruta se ejecute.

2.4 APIRouter: rutas agrupadas

Un APIRouter es un grupo de rutas con un prefijo común. routers/ventas.py crea uno con prefix="/ventas", así que @router.post("") atiende POST /ventas. En main.py, app.include_router(ventas.router) suma esas rutas a la aplicación. El parámetro tags agrupa las rutas en /docs.

2.5 Dos tipos de validación

El schema valida la forma: que cantidad sea un número mayor que cero con hasta 3 decimales. El service valida las reglas del negocio, que dependen de los datos guardados: que el producto exista, que haya stock suficiente y que no se vendan fracciones de un producto que se vende por unidad. Pydantic no puede saber que la leche se vende por unidad, porque eso depende del producto elegido.

Cuando una regla no se cumple, el service lanza un error propio del negocio, como StockInsuficiente. Ese error no sabe nada de HTTP. En main.py, un manejador de excepciones (@app.exception_handler) lo atrapa y elige el código: 404, 409 o 422.

2.6 Primero validar, después modificar

ServicioVentas.registrar trabaja en dos fases. Primero recorre todas las líneas y comprueba todas las reglas sin modificar nada. Solo si todas pasan, descuenta el stock y guarda la venta. Si la segunda línea no tuviera stock, la primera no quedaría descontada a medias. En el módulo 05 esta misma garantía la da una transacción de la base de datos.

2.7 Paquetes e imports en Python

Una carpeta con un archivo __init__.py es un paquete: Python la trata como un módulo que contiene otros. El código importa con rutas absolutas desde el paquete app, por ejemplo from app.services.ventas import ServicioVentas. Para que Python encuentre app, el servidor se lanza desde la carpeta de la etapa: fastapi dev app/main.py.

3. Código mínimo

El router queda reducido a traducir HTTP. La regla del stock no aparece:

router = APIRouter(prefix="/ventas", tags=["ventas"])

@router.post("", status_code=status.HTTP_201_CREATED)
def registrar_venta(venta: VentaIn, servicio: ServicioVentasDep) -> VentaOut:
    return servicio.registrar(venta)

El service concentra las reglas y no importa nada de FastAPI:

for item in venta.items:
    producto = self.productos.obtener(item.producto_id)
    if producto is None:
        raise ProductoNoEncontrado(item.producto_id)
    if producto.unidad == "unidad" and item.cantidad != item.cantidad.to_integral_value():
        raise CantidadInvalida(producto.nombre)
    if producto.stock < item.cantidad:
        raise StockInsuficiente(producto.nombre, producto.stock, item.cantidad)

main.py traduce cada error del negocio a un código HTTP:

CODIGOS_HTTP = {ProductoNoEncontrado: 404, StockInsuficiente: 409, CantidadInvalida: 422}

@app.exception_handler(ErrorDeNegocio)
def manejar_error_de_negocio(request: Request, error: ErrorDeNegocio) -> JSONResponse:
    codigo = CODIGOS_HTTP.get(type(error), 400)
    return JSONResponse(status_code=codigo, content={"detail": str(error)})

Se ejecuta desde la carpeta de la etapa:

fastapi dev app/main.py       # la API completa
python probar_service.py      # el mismo service, sin servidor

6. Errores comunes

Lanzar HTTPException desde un service.

Funciona en la API, pero ata el service a HTTP. Si el bot usa ese service, recibe un error con un código 409 que no significa nada en Telegram. El service lanza errores del negocio y la capa de HTTP los traduce.

Ejecutar fastapi dev main.py desde la carpeta app.

Python no encuentra el paquete app y falla con ModuleNotFoundError: No module named 'app'. Se ejecuta desde la carpeta de la etapa: fastapi dev app/main.py.

Importaciones circulares.

Si un service importa algo de un router y el router importa el service, Python falla con un error de módulo «parcialmente inicializado». Respetar la dirección router → service → repository lo evita.

Crear el repositorio en memoria dentro de la dependencia.

Si obtener_servicio_ventas() hiciera RepositorioProductos() en cada llamada, cada petición empezaría con el stock original y las ventas se perderían. Por eso los repositorios en memoria se crean una sola vez. En el módulo 05 pasa lo contrario: se abre una sesión de base de datos nueva por petición.

Cambiar un schema de entrada sin avisar a los clientes.

Al agregar stock como obligatorio en ProductoIn, el cliente.py del módulo 01 empezó a recibir 422 al crear productos. Un campo nuevo obligatorio rompe el contrato; uno opcional con valor por defecto, no.

7. Ejercicios

1. Sin mirar la Tabla 2, ¿qué archivos tocarías para (a) cambiar el texto del error de stock, (b) agregar la ruta GET /ventas/{venta_id} y (c) que el token se lea de una variable de entorno con otro nombre?

Ver respuesta

(a) Solo errores.py. (b) repositories/memoria.py (método obtener), services/ventas.py (lanza un error si no existe), errores.py (el error nuevo), main.py (su código 404) y routers/ventas.py (la ruta). (c) Solo config.py.

2. Reiniciá el servidor y enviá {"items": [{"producto_id": 1, "cantidad": "1.5"}, {"producto_id": 1, "cantidad": "1.5"}]}. Hay 2,1 kg de queso. ¿Qué pasa con el stock? ¿Dónde está el error y cómo se arregla?

Ver respuesta

La venta se acepta y el stock queda en −0,9 kg. Cada línea se compara por separado contra el stock original (1,5 ≤ 2,1), pero juntas suman 3 kg. El error está en services/ventas.py. Se arregla sumando primero las cantidades pedidas de cada producto (por ejemplo, con un diccionario producto_id → cantidad total) y comparando esa suma con el stock.

3. Buscá la palabra fastapi dentro de app/services/ y de app/repositories/. ¿Aparece? ¿Por qué importa?

Ver respuesta

No aparece. Por eso esas capas se pueden usar desde probar_service.py, desde un bot o desde una prueba automática sin levantar un servidor.

4. En probar_service.py, creá un repositorio de productos con todo el stock en cero (por ejemplo, una clase que herede de RepositorioProductos y lo modifique en su __init__) y pasáselo al service. ¿Tuviste que cambiar ServicioVentas?

Ver respuesta

No. El service recibe el repositorio desde afuera, así que funciona con cualquier objeto que tenga los mismos métodos. Todas las ventas se rechazan con StockInsuficiente. Esa es la misma idea que usan las pruebas automáticas para probar reglas sin base de datos.
