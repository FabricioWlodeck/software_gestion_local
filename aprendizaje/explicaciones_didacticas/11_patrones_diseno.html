Patrones de diseño y cómo decidir cuándo usarlos

Qué es un patrón, cuáles aparecieron ya en los módulos 03 a 10, tres patrones nuevos para el proyecto real (uno para la base, uno para el backend y uno para el frontend) y qué tener en cuenta al tomar una decisión de diseño.

Por qué este módulo va al final. Un patrón se entiende cuando ya se vio el problema que resuelve. Con las etapas 03 a 10 hechas, casi todos los patrones de este módulo señalan código que ya existe y funciona. Además, el módulo sirve de puente hacia el diseño del sistema real.

1. Problema

Al pasar del mini Punto Lácteo al sistema real aparecen preguntas que el material no resolvió. Si el stock del queso no coincide con lo vendido, ¿cómo se sabe quién lo cargó, quién lo ajustó y por qué? Si el precio se calcula a veces con un margen sobre el costo y a veces a mano, ¿dónde va esa regla? Si el carrito suma descuentos y medios de pago, ¿cuántas funciones más tiene que manejar la pantalla de ventas?

Estos problemas tienen soluciones conocidas y con nombre, que se llaman patrones de diseño. También existe el riesgo opuesto: llenar el código de capas, interfaces y clases que no resuelven ningún problema concreto y que alguien tiene que leer y mantener. Este módulo da los nombres y, sobre todo, un criterio para decidir cuándo conviene aplicar cada uno.

2. Concepto

2.1 Qué es un patrón

Un patrón de diseño es una solución probada a un problema que se repite, descrita con un nombre, el contexto en el que sirve y lo que cuesta aplicarla. La idea viene de la arquitectura de edificios: Christopher Alexander la propuso en 1977. Llegó al software con el libro Design Patterns (Gamma, Helm, Johnson y Vlissides, 1994), que reunió 23 patrones de programación orientada a objetos. En 2002, Martin Fowler publicó un catálogo para aplicaciones con base de datos, de donde salen Repository, Service Layer y Unit of Work.

El nombre es la mitad del valor de un patrón. Decir «esto es un repository» le explica a otra persona, por ejemplo al profesor que revisa el código, qué hace una clase y qué no hace, sin que tenga que leerla entera. La otra mitad es el problema: un patrón aplicado donde no existe su problema solo agrega código.

2.3 Para la base: libro de movimientos

En las etapas anteriores, el stock es una columna que cada venta sobrescribe. Si el queso marca 0,700 kg cuando debería haber 2,950, la columna no puede decir qué pasó, porque cada UPDATE borró el valor anterior.

Un libro de movimientos guarda cada cambio como una fila nueva de movimiento_stock, con el tipo (compra, venta, ajuste o merma), la cantidad con signo, el usuario, la fecha y el motivo. Las filas no se modifican ni se borran: un error se corrige con otro movimiento. El stock es la suma de las cantidades. Es la misma idea que el libro diario de la contabilidad, y su versión general, donde todo el estado de un sistema se reconstruye a partir de eventos, se llama event sourcing.

Sumar todas las filas en cada consulta sería lento con años de movimientos. Por eso la columna producto.stock se conserva como saldo, una desnormalización deliberada como la de venta.total: cada operación inserta el movimiento y actualiza el saldo en la misma transacción. Dos restricciones CHECK protegen el libro: el signo tiene que corresponder al tipo, y los ajustes y las mermas exigen un motivo.

MariaDB ofrece además tablas versionadas del sistema (WITH SYSTEM VERSIONING), que guardan cada versión de una fila sin escribir código y permiten consultar la tabla en una fecha pasada con FOR SYSTEM_TIME AS OF. Sirven para el historial de precios, pero no reemplazan al libro: guardan el valor anterior, no el tipo de movimiento ni el motivo.

El mismo principio, no borrar lo que pasó y registrar el cambio, se aplica a las ventas. Una venta que no tiene que contar se marca con un estado y queda en la base, en lugar de eliminarse con DELETE.

2.4 Para el backend: Estrategia

El patrón Estrategia (Strategy) agrupa varias formas de hacer lo mismo detrás de una interfaz común. En la etapa, el precio se puede fijar con un margen sobre el costo (PrecioPorMargen) o a mano (PrecioManual). Las dos clases tienen el método calcular(costo), y el service llama a ese método sin saber cuál de las dos recibió.

La base guarda dos columnas, modo_precio y valor_precio. Una fábrica, estrategia_para(), las traduce al objeto que corresponde, igual que requerir_rol() fabrica una dependencia en el módulo 06. La interfaz se declara con Protocol: cualquier clase que tenga calcular con esa firma cumple, sin heredar de nada, como pasa con las interfaces de TypeScript.

Con dos modos, un if hace exactamente lo mismo y se lee igual de bien. La estrategia empieza a pagar con el tercer modo, por ejemplo un descuento o un precio mayorista, o cuando cada modo tiene sus propios datos y validaciones. A partir de ahí, cada caso nuevo es una clase nueva y ninguna de las existentes cambia.

2.5 Para el frontend: reducer y hook personalizado

En la etapa 09, PantallaVentas tiene el carrito en un useState y tres funciones que lo modifican, mezcladas con la carga de productos y el cobro. Cada descuento o medio de pago nuevo agregaría otra función a la pantalla.

Un reducer es una función pura que recibe el estado actual y una acción (un objeto que describe qué pasó, como { tipo: "quitar", productoId: 2 }) y devuelve el estado nuevo. Todas las formas de cambiar el carrito quedan en carritoReducer.ts, que no importa React y se prueba con Node solo. useReducer guarda el estado y devuelve dispatch: llamarlo con una acción ejecuta el reducer y vuelve a dibujar el componente.

El hook personalizado useCarrito() envuelve todo eso y le ofrece a la pantalla tres funciones: agregar, quitar y vaciar. Antes de que existieran los hooks, la lógica se separaba de la vista con componentes «contenedores»; hoy se separa con hooks como este. Los componentes de presentación (TarjetaProducto, Carrito) no cambian: siguen recibiendo datos y avisando eventos. Para un estado con uno o dos cambios simples, useState sigue siendo más claro.

2.6 Qué tener en cuenta al tomar una decisión de diseño

Un patrón responde a un problema; nunca es un objetivo en sí mismo. Estas preguntas, en este orden, sirven para cualquier decisión de diseño, sea un patrón, una biblioteca o la forma de una tabla.

  1. ¿Qué problema concreto hay hoy? Si no se puede describir con un caso del negocio, como «la dueña quiere saber quién ajustó el queso», todavía no hace falta la solución. Es el principio YAGNI (You Aren't Gonna Need It o No Lo Vas a Necesitar).

  2. ¿Cuánto cuesta cambiarla después? Algunas decisiones son caras de revertir: el esquema de la base, cómo se representan el dinero y el peso, qué historial se guarda y cómo se autentica a los usuarios. Otras son baratas: la biblioteca de componentes, los nombres de carpetas o los estilos. Se dedica tiempo a las primeras y se deciden rápido las segundas. Las decisiones sobre historial están entre las más caras, porque un dato que no se guardó no se puede reconstruir después.

  3. ¿Qué cambia junto y qué cambia por separado? Lo que cambia por el mismo motivo va junto, y a eso se le llama cohesión. Lo que cambia por motivos distintos se separa, para que un cambio no rompa lo otro, y a eso se le llama bajo acoplamiento. Las capas del módulo 03 son esta idea aplicada.

  4. ¿Hay al menos tres casos? La regla de tres dice que la primera vez se escribe, la segunda se duplica y a la tercera se abstrae. Sandi Metz sostiene que duplicar cuesta menos que mantener una abstracción equivocada, porque una abstracción mala obliga a agregarle parámetros y condiciones con cada caso nuevo.

  5. ¿Se puede probar por partes? Si para probar un cálculo hacen falta la base, el servidor y el navegador, las piezas están acopladas. El reducer y la estrategia de la etapa se prueban solos.

  6. ¿Sigue las convenciones del framework? FastAPI resuelve dependencias con Depends y React reutiliza lógica con hooks. Un patrón que pelea con el framework, como armar a mano un contenedor de dependencias en FastAPI, cuesta más y sorprende a quien ya conoce el framework.

  7. ¿Quién lo va a leer y mantener? El profesor va a revisar el código y el mantenimiento queda a cargo de una sola persona. Se prefiere el código que se entiende sin explicación al código ingenioso.

  8. ¿Cuáles son las restricciones reales? El plazo de la expo, una sola persona desarrollando, el servidor de la facultad y MariaDB como motor. Una solución que no entra en esas restricciones no es una opción, por buena que sea en otro contexto.

  9. ¿Quedó escrito el porqué? El código muestra qué se hizo, pero no por qué ni qué se descartó. Para eso están los registros de la sección 2.7.

2.7 Registros de decisiones de arquitectura

Un ADR (Architecture Decision Record o Registro de Decisión de Arquitectura) es un archivo corto que guarda una decisión importante con su contexto, las opciones consideradas, lo que se decidió y sus consecuencias, incluidas las negativas. El formato lo propuso Michael Nygard en 2011. Los registros se numeran, se guardan en el repositorio y no se borran: si una decisión cambia, se escribe uno nuevo con estado «Reemplaza a 0002», y el viejo pasa a «Reemplazada por 0005».

La carpeta decisiones/ de la etapa tiene la plantilla y tres ejemplos. Dos documentan decisiones ya tomadas en el material (DECIMAL para dinero y peso, y el token en localStorage). El tercero, el stock como libro de movimientos, tiene estado «Propuesta»: se acepta o se rechaza al diseñar el sistema real. Dentro de seis meses, o cuando el profesor pregunte por qué el stock no es una columna, la respuesta está escrita.

3. Código mínimo

El libro de movimientos en bd/libro_de_movimientos.sql (resumido):

CREATE TABLE movimiento_stock (
    id           INT            AUTO_INCREMENT PRIMARY KEY,
    producto_id  INT            NOT NULL,
    tipo         VARCHAR(10)    NOT NULL,
    cantidad     DECIMAL(10, 3) NOT NULL,  -- con signo: positiva entra, negativa sale
    usuario      VARCHAR(40)    NOT NULL,
    motivo       VARCHAR(120)   NULL,
    fecha        DATETIME       NOT NULL,
    CONSTRAINT ck_movimiento_signo CHECK (
        (tipo = 'compra' AND cantidad > 0)
        OR (tipo IN ('venta', 'merma') AND cantidad < 0)
        OR (tipo = 'ajuste' AND cantidad <> 0)
    )
);

-- El stock es la suma; el saldo de cada fila, una función de ventana.
SELECT fecha, tipo, cantidad, usuario,
       SUM(cantidad) OVER (ORDER BY fecha, id) AS saldo
FROM movimiento_stock
WHERE producto_id = 1;

La estrategia de precios en backend/precios.py:

class EstrategiaDePrecio(Protocol):
    def calcular(self, costo: Decimal) -> Decimal: ...

@dataclass(frozen=True)
class PrecioPorMargen:
    porcentaje: Decimal  # 35 significa 35 % sobre el costo

    def calcular(self, costo: Decimal) -> Decimal:
        return (costo * (1 + self.porcentaje / 100)).quantize(CENTAVOS, rounding=ROUND_HALF_UP)

@dataclass(frozen=True)
class PrecioManual:
    precio: Decimal

    def calcular(self, costo: Decimal) -> Decimal:
        return self.precio  # el costo no influye: la dueña lo fijó a mano

El reducer y el hook del carrito en frontend/:

export type AccionCarrito =
  | { tipo: "agregar"; producto: Producto; cantidad: string }
  | { tipo: "quitar"; productoId: number }
  | { tipo: "vaciar" };

export function carritoReducer(items: ItemCarrito[], accion: AccionCarrito): ItemCarrito[] {
  switch (accion.tipo) {
    case "agregar":
      return [...items.filter((item) => item.producto.id !== accion.producto.id),
              { producto: accion.producto, cantidad: accion.cantidad }];
    case "quitar":
      return items.filter((item) => item.producto.id !== accion.productoId);
    case "vaciar":
      return [];
  }
}

export function useCarrito() {
  const [items, dispatch] = useReducer(carritoReducer, CARRITO_VACIO);
  return {
    items,
    agregar: (producto: Producto, cantidad: string) => dispatch({ tipo: "agregar", producto, cantidad }),
    quitar: (productoId: number) => dispatch({ tipo: "quitar", productoId }),
    vaciar: () => dispatch({ tipo: "vaciar" }),
  };
}

6. Errores comunes

Aplicar un patrón porque aparece en un libro.

El código se alarga sin que haya un problema que lo justifique, y quien lo lee busca un motivo que no existe. Antes de aplicar un patrón, hay que poder nombrar el caso del negocio que lo pide.

Crear una interfaz «por si mañana cambiamos».

Una interfaz con una sola implementación se justifica si separa algo que cambia por otro motivo, como el repository que aísla el SQL de las reglas. Si su único motivo es un cambio que nadie pidió, es costo sin beneficio.

Abstraer con el segundo caso.

Dos casos parecidos todavía no muestran qué tienen en común y qué no. La abstracción que sale de ahí suele necesitar parámetros y condiciones nuevas con el tercer caso. Duplicar una vez y esperar es más barato.

Borrar registros del negocio.

Un DELETE de una venta o un UPDATE que pisa el stock eliminan la única prueba de lo que pasó. Se registra un cambio de estado o un movimiento nuevo, y la historia queda.

Poner reglas del negocio en el router o en el componente.

Cuando el bot de Telegram necesite consultar el stock, la regla tendría que duplicarse. En el service, el bot y la API usan el mismo código.

Copiar la arquitectura de un sistema grande.

Microservicios, colas de mensajes o bases separadas para lectura y escritura resuelven problemas de equipos y volúmenes que Punto Lácteo no tiene. Para dos locales alcanza con un backend y una base, bien organizados por dentro.

2. Agregá a precios.py una estrategia PrecioConDescuento que aplique un porcentaje de descuento sobre el precio de otra estrategia. ¿Qué clases existentes tuviste que modificar?

Ver respuesta 
@dataclass(frozen=True)
class PrecioConDescuento:
    base: EstrategiaDePrecio
    descuento: Decimal  # 10 significa 10 % menos

    def calcular(self, costo: Decimal) -> Decimal:
        precio = self.base.calcular(costo)
        return (precio * (1 - self.descuento / 100)).quantize(CENTAVOS, rounding=ROUND_HALF_UP)

Ninguna. PrecioConDescuento(PrecioPorMargen(Decimal("35")), Decimal("10")).calcular(Decimal("9800.00")) devuelve 11907.00. Como envuelve a otra estrategia, el descuento funciona sobre cualquiera de las dos. Solo la fábrica necesitaría un modo nuevo para crearla a partir de la base.

Solo PantallaVentas. Las partes que cambian:

import { useCarrito } from "./useCarrito";

5. Con decisiones/plantilla.md, escribí el registro 0004 para una decisión pendiente del sistema real: cómo se marca una venta que no tiene que contar en los totales.

Ver respuesta

No hay una única respuesta correcta, pero un buen registro incluye lo siguiente. El contexto explica que un empleado no puede anular una venta y que la dueña necesita saber quién marcó cada una. Las opciones son, por ejemplo, borrar la venta, una columna estado con valores como valida y observada, o una tabla aparte de observaciones con usuario, fecha y motivo. Las consecuencias dicen qué consultas cambian (todos los totales filtran por estado) y qué se pierde con cada opción. El estado del registro es «Propuesta» hasta que se decida.

8. Documentación y lecturas

Las lecturas están ordenadas por prioridad. Con el plazo de la expo alcanza con las de 8.1, que son artículos cortos; el resto sirve para consultar durante el proyecto real y para seguir después.

8.1 Para leer antes de empezar el proyecto

  • Martin Fowler: «Yagni» (en inglés). Explica qué cuesta construir algo antes de necesitarlo, incluso cuando al final se termina usando.
  • Sandi Metz: «The Wrong Abstraction» (en inglés). Por qué una abstracción equivocada sale más cara que el código duplicado y cómo deshacerla.
  • Michael Nygard: «Documenting Architecture Decisions» (en inglés). El artículo original de los ADR, con el formato que usa la plantilla de la etapa.
  • React: Extraer la lógica de estado en un reducer. La explicación oficial de useReducer, con un ejemplo parecido al carrito.

8.2 En línea y gratis, para consultar durante el proyecto

  • Harry Percival y Bob Gregory: Architecture Patterns with Python (en inglés). Libro completo y gratuito sobre Repository, Service Layer y Unit of Work en Python con SQLAlchemy. Usa Flask, pero los patrones se trasladan igual a FastAPI. Los capítulos más útiles son el 2, el 4 y el 6.
  • Martin Fowler: catálogo de Patterns of Enterprise Application Architecture (en inglés). Una ficha por patrón, entre ellas Repository, Service Layer y Unit of Work. Su artículo sobre Event Sourcing es la versión general del libro de movimientos.
  • Refactoring.Guru: patrones de diseño. Los patrones clásicos con ilustraciones y ejemplos en Python y TypeScript. Sirven en especial Strategy y Adapter, que encaja con el bot de Telegram: un notificador con la misma interfaz para Telegram o para la consola.
  • Lydia Hallie y Addy Osmani: patterns.dev (en inglés). Patrones de JavaScript y React, entre ellos el de hooks, el de contenedor y presentación y el de provider.
  • React, documentación oficial: Reutilizar lógica con Hooks personalizados, Elegir la estructura del estado, Quizás no necesites un Efecto y Pasar datos en profundidad con contexto.
  • The Twelve-Factor App. Doce reglas para aplicaciones que se despliegan en servidores, como la configuración por variables de entorno de los módulos 06 y 10.
  • adr.github.io (en inglés). Otras plantillas de ADR y herramientas para mantenerlos.
  • MariaDB: tablas versionadas del sistema (en inglés). Referencia de WITH SYSTEM VERSIONING y FOR SYSTEM_TIME AS OF.
  • Documentación usada en la etapa: Python: módulo typing, con Protocol, FastAPI: aplicaciones más grandes, FastAPI: dependencias y SQLAlchemy: la sesión (en inglés).

8.3 Un libro corto

  • John Ousterhout: A Philosophy of Software Design, 2.ª edición, 2021 (en inglés). Tiene menos de 200 páginas y no es gratuito. Trata la complejidad como el problema central del diseño y propone módulos «profundos», con una interfaz simple que esconde mucho trabajo. Ayuda a reconocer cuándo una capa o una clase no aporta nada.

8.4 Cursos gratuitos

  • Universidad de Helsinki: Full Stack Open, en español. Las partes de React aplican directo al proyecto, en especial la parte 7, con hooks personalizados. El backend del curso usa Node en lugar de Python.
  • Harvard: CS50's Introduction to Databases with SQL (en inglés). Tiene semanas sobre diseño de esquemas, optimización y escalado. Usa SQLite y, en la semana de escalado, MySQL y PostgreSQL.
  • MIT 6.102: Software Construction (en inglés). Lecturas públicas en TypeScript sobre especificaciones, tipos abstractos de datos e interfaces. Es más exigente que los anteriores: conviene para después de la expo.

8.5 De Anthropic

Anthropic no publica material sobre patrones de diseño de software en general. Lo que publica sirve para dos cosas relacionadas: diseñar sistemas que usan modelos de lenguaje y trabajar con Claude Code en el proyecto.

  • Anthropic: «Building effective agents» (en inglés). Trata sobre sistemas con modelos de lenguaje, pero su regla central vale para cualquier diseño: buscar la solución más simple posible y sumar complejidad solo cuando hace falta.
  • Claude Code: buenas prácticas (en inglés). Recomienda conversar primero hasta tener una especificación escrita y recién después implementar, darle a Claude una prueba que pueda ejecutar para verificar su trabajo, y anotar en CLAUDE.md solo lo que no se deduce leyendo el repositorio, como las decisiones no documentadas. Esas decisiones son justamente las que guardan los ADR.
  • Anthropic Academy: cursos gratuitos, entre ellos Claude Code 101 y Claude Code in Action, para usar Claude Code en el desarrollo diario.
