JavaScript vs TypeScript: el mismo error, antes o después

El JavaScript mínimo para usar React, qué agrega TypeScript, cuánto cuesta y por qué el proyecto lo usa.

1. Problema

El navegador solo ejecuta JavaScript, así que el frontend de Punto Lácteo se escribe en JavaScript o en algo que se convierta en JavaScript. Para alguien que viene de Python hay dos dificultades. La primera es la sintaxis, que cambia en detalles todo el tiempo. La segunda es más seria: JavaScript deja pasar errores que Python habría frenado. Suma un texto y un número sin quejarse, devuelve undefined al leer una propiedad mal escrita y recién falla cuando la cajera toca el botón que ejecuta esa línea.

Además, el contrato de la API (los campos de ProductoOut, el tipo de cada uno) está escrito en Python, y el frontend no tiene forma de saberlo. TypeScript agrega tipos a JavaScript y los verifica antes de ejecutar. Este módulo muestra el mismo carrito con los mismos tres errores en los dos lenguajes.

2. Concepto

2.1 JavaScript dentro y fuera del navegador

JavaScript es el único lenguaje que los navegadores ejecutan de forma nativa. Node.js es un programa que ejecuta JavaScript fuera del navegador, en la terminal. La etapa 07 usa Node para probar el lenguaje sin pantallas, y los módulos 08 y 09 lo usan para las herramientas de desarrollo (Vite, npm). El código del frontend, en cambio, corre en el navegador de la cajera.

async/await merece una aclaración. Cuando el frontend le pide algo al backend, la respuesta tarda. await espera esa respuesta sin congelar la pantalla, y el resto del programa sigue corriendo mientras tanto. Por eso, en 01_fundamentos.js, la última línea se imprime antes de que lleguen los productos.

2.3 Tipado dinámico y conversiones silenciosas

En JavaScript, como en Python, las variables no declaran tipo. La diferencia es qué pasa al mezclar tipos. Python rechaza "2" + 1 con un TypeError; JavaScript lo convierte en "21". Leer una propiedad que no existe no es un error: devuelve undefined, y operar con undefined da NaN (Not a Number o «no es un número»). El programa sigue como si nada, con un resultado incorrecto.

2.4 Qué es TypeScript

TypeScript es JavaScript con anotaciones de tipo. Todo JavaScript válido es TypeScript válido; TypeScript solo agrega sintaxis como precio: number. Lo importante es cuándo actúa: los tipos se verifican mientras se escribe (el editor subraya los errores) o con el comando tsc, y después se borran. Lo que ejecuta el navegador o Node es JavaScript sin tipos. Por eso node 03_carrito_con_errores.ts falla exactamente igual que la versión en JavaScript: los tipos no existen al ejecutar.

Vite, que se usa en el módulo 08, también borra los tipos sin verificarlos para que el servidor de desarrollo sea rápido. La verificación la hacen el editor y el comando de compilación (npm run build ejecuta tsc antes de empaquetar).

2.5 Los tipos que se usan

Una interface describe la forma de un objeto, igual que un schema de Pydantic. Una unión como "kg" | "unidad" limita los valores posibles, como Literal. Producto | undefined declara que un valor puede faltar. Con "strict": true en tsconfig.json, TypeScript obliga a contemplar ese caso antes de usar el valor. En muchos lugares no hace falta anotar: TypeScript infiere el tipo. En let total = 0 ya sabe que total es un number.

3. Código mínimo

La misma función, primero en JavaScript y después en TypeScript:

// JavaScript: nada dice qué es "id" ni qué devuelve
function buscarProducto(id) {
  return productos.find((producto) => producto.id === id);
}

// TypeScript: recibe un número y devuelve un Producto, o undefined si no lo encuentra
function buscarProducto(id: number): Producto | undefined {
  return productos.find((producto) => producto.id === id);
}

El contrato de la API como interfaz, espejo de ProductoOut:

interface Producto {
  id: number;
  nombre: string;
  unidad: "kg" | "unidad";
  precio: string;   // Decimal llega como texto
  stock: string;
}

Comandos desde la carpeta de la etapa:

npm install                     # instala el compilador de TypeScript (una vez)
node 02_carrito.js              # JavaScript: resultados incorrectos y un error al final
node 03_carrito_con_errores.ts  # TypeScript ejecutado: lo mismo, los tipos se borran
npx tsc --noEmit                # TypeScript verificado: los errores, sin ejecutar
node 04_carrito_corregido.ts    # la versión corregida

6. Errores comunes

Creer que TypeScript valida los datos al ejecutar.

Si la API devuelve precio como número y la interfaz dice string, TypeScript no se entera: los tipos ya no existen. Las interfaces describen lo que se espera; si el backend cambia el contrato, hay que actualizarlas.

Usar any para que desaparezcan los errores.

any apaga la verificación para ese valor y todo lo que se derive de él. Es volver a JavaScript sin avisarle a nadie. Cuando no se sabe el tipo, unknown obliga a comprobarlo antes de usarlo.

Usar == en lugar de ===.

"2" == 2 es verdadero porque == convierte tipos antes de comparar. === compara valor y tipo, que es lo que se espera viniendo de Python.

Olvidar el await.

Sin await, pedirProductos() devuelve una promesa (una respuesta «pendiente»), no la lista. El código siguiente trabaja con la promesa y falla de formas confusas. TypeScript suele detectarlo, porque el tipo es Promise<Producto[]> y no Producto[].

Calcular dinero con number.

1450 * 1.1 da 1595.0000000000002. Para mostrar alcanza con redondear al formatear. Los cálculos que importan (totales, stock) los hace el backend con Decimal.

2. En 04_carrito_corregido.ts, cambiá unidad: "kg" del queso por unidad: "litro" y ejecutá npx tsc --noEmit. ¿Qué dice? ¿Qué pasa si lo ejecutás con node?

Ver respuesta

tsc informa que "litro" no se puede asignar al tipo "kg" | "unidad". Con node se ejecuta sin problemas, porque los tipos se borran. Es la misma protección que Literal en Pydantic, pero en el momento de escribir el código.

3. Reescribí el bucle de la cantidad total de 04_carrito_corregido.ts con reduce, sin perder la conversión a número.

const cantidadTotal = carrito.reduce((suma, item) => suma + Number(item.cantidad), 0);

4. En 01_fundamentos.js, ¿por qué «esta línea se imprime ANTES» aparece antes que «llegaron 3 productos», si está escrita después de llamar a cargar()?

Ver respuesta

cargar() llega al await y le devuelve el control al programa mientras espera los 300 ms. El programa sigue con la línea siguiente y la imprime. Cuando la promesa se resuelve, cargar continúa e imprime el mensaje de llegada. En una pantalla, eso evita que la interfaz se congele mientras espera al backend.
