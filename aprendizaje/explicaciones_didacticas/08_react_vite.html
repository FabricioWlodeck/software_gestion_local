React + Vite: una interfaz hecha de componentes

Cómo se crea, declara e inicializa un proyecto de React con Vite, cómo se arma una pantalla con componentes, props y estado, y qué aporta una librería de componentes como Mantine.

1. Problema

La pantalla de caja cambia todo el tiempo. Cuando la cajera agrega queso, hay que sumar una línea al carrito, recalcular el total, habilitar el botón Cobrar y, quizás, mostrar un error en la tarjeta del producto. Con JavaScript solo, cada uno de esos cambios se programa a mano: buscar el elemento de la página, modificarlo y acordarse de modificar todos los que dependen de él. Con diez pantallas, mantener todo sincronizado se vuelve imposible.

React invierte el enfoque. El programador describe cómo se ve la pantalla para un estado dado («con este carrito, se ve así»), y cuando el estado cambia, React vuelve a calcular la pantalla y modifica solo lo necesario. Vite es la herramienta que convierte ese código (TypeScript con JSX) en algo que el navegador entiende, y lo actualiza al instante mientras se programa.

2. Concepto

2.1 Qué hace Vite

El navegador no entiende TypeScript ni JSX, y tampoco conviene enviarle cientos de archivos sueltos. Vite resuelve las dos cosas en dos modos. En desarrollo (npm run dev), levanta un servidor en http://localhost:5173, transforma cada archivo cuando el navegador lo pide y, al guardar, reemplaza solo el módulo modificado sin recargar la página. Eso se llama HMR (Hot Module Replacement o Reemplazo de Módulos en Caliente), y conserva el estado: el carrito sigue lleno después de guardar un cambio. En producción (npm run build), Vite verifica los tipos con tsc, empaqueta todo en unos pocos archivos optimizados dentro de dist/ y termina. Esos archivos son estáticos: los puede servir cualquier servidor web, y en el módulo 10 los sirve nginx.

Node.js y npm (Node Package Manager o Gestor de Paquetes de Node) solo se usan para desarrollar y construir. En el navegador de la cajera corre el resultado de dist/, sin Node.

2.3 Cómo arranca la aplicación

El navegador pide index.html, que tiene un <div id="root"> vacío y una etiqueta <script type="module" src="/src/main.tsx">. main.tsx busca ese div y ejecuta createRoot(...).render(<App />). A partir de ahí, React llama a la función App, que devuelve el encabezado y <PantallaVentas />; React llama a PantallaVentas, y así sigue hasta las hojas del árbol. Toda la interfaz se dibuja dentro de ese único div.

2.4 Componentes y JSX

Un componente es una función que devuelve lo que se ve. Su nombre empieza con mayúscula y lo que devuelve se escribe en JSX, una sintaxis parecida a HTML que Vite convierte en llamadas a funciones. Tiene algunas diferencias con HTML: class se escribe className, las expresiones de TypeScript van entre llaves ({producto.nombre}), y lo que devuelve un componente tiene un solo elemento raíz (o un fragmento <>...</>). Los archivos con JSX y TypeScript terminan en .tsx.

2.5 Props: datos de padre a hijo

Un componente recibe datos de su padre mediante props, que son los parámetros de la función. <TarjetaProducto producto={queso} onAgregar={agregar} /> le pasa un producto y una función. Las props se declaran con una interfaz de TypeScript, así que pasar un dato del tipo equivocado es un error de compilación. Un componente nunca modifica sus props. Para avisarle algo al padre, llama a una función que el padre le pasó: onAgregar(producto, cantidad). Los datos bajan por props y los avisos suben por funciones.

2.6 Estado

El estado son los datos que cambian mientras la pantalla está abierta. Se crea con useState: const [carrito, setCarrito] = useState<ItemCarrito[]>([]) devuelve el valor actual y una función para cambiarlo. Cada vez que se llama a setCarrito, React vuelve a ejecutar el componente con el valor nuevo y actualiza lo que cambió en pantalla.

El estado se reemplaza, no se modifica. carrito.push(item) cambia el arreglo existente, React compara y ve el mismo arreglo, y la pantalla no se actualiza. Se crea uno nuevo con el operador spread del módulo 07: setCarrito([...carrito, item]).

La pregunta clave es dónde vive cada estado. La regla es ponerlo en el componente más cercano que abarque a todos los que lo usan. El carrito lo usan la lista (para agregar) y el carrito (para mostrar), así que vive en PantallaVentas, que es su padre común. La cantidad que se está escribiendo en una tarjeta solo le importa a esa tarjeta, así que vive en TarjetaProducto.

2.7 Estado derivado

El total del carrito no es estado: se calcula a partir del carrito cada vez que el componente se dibuja. Guardarlo aparte obligaría a mantener dos datos sincronizados, que es justamente el problema que React evita. Es la misma idea que en la base de datos (módulo 04): cada dato se guarda en un solo lugar.

2.8 Listas y key

Para dibujar una lista se usa map, y cada elemento lleva una key única: {productos.map((p) => <TarjetaProducto key={p.id} ... />)}. La key le permite a React saber qué elemento es cuál entre un dibujo y el siguiente. Sin ella, si la lista se reordena, el estado local de una tarjeta (la cantidad escrita) podría quedar en la tarjeta equivocada.

2.9 Efectos

Dibujar debe ser un cálculo sin efectos secundarios. Lo que interactúa con el mundo exterior (pedir datos al backend, programar un temporizador) va en useEffect, que se ejecuta después de dibujar. El segundo argumento es la lista de dependencias: con [], el efecto se ejecuta una sola vez, al aparecer el componente. PantallaVentas lo usa para cargar los productos, mientras muestra «Cargando productos…».

2.10 Carpetas por funcionalidad

El código se agrupa por funcionalidad, no por tipo de archivo: todo lo de la pantalla de ventas (componentes y estilos) está en src/features/ventas/. Cuando se agreguen las pantallas de stock e historial, cada una tendrá su carpeta, y un cambio en ventas no obliga a buscar archivos repartidos por todo el proyecto. Lo compartido (tipos, formatos) queda afuera, en tipos.ts y utilidades/.

3. Código mínimo

Un componente con props tipadas y estado local (TarjetaProducto.tsx, resumido):

interface Props {
  producto: Producto;
  onAgregar: (producto: Producto, cantidad: string) => void;
}

export function TarjetaProducto({ producto, onAgregar }: Props) {
  const [cantidad, setCantidad] = useState("0.250");

  return (
    <article className="tarjeta-producto">
      <h3>{producto.nombre}</h3>
      <input value={cantidad} onChange={(evento) => setCantidad(evento.target.value)} />
      <button onClick={() => onAgregar(producto, cantidad)}>Agregar</button>
    </article>
  );
}

El dueño del estado compartido (PantallaVentas.tsx, resumido):

const [productos, setProductos] = useState<Producto[]>([]);
const [carrito, setCarrito] = useState<ItemCarrito[]>([]);

useEffect(() => {
  cargarProductosDePrueba().then(setProductos);
}, []);

function agregar(producto: Producto, cantidad: string) {
  setCarrito((anterior) => [...anterior, { producto, cantidad }]);
}

return (
  <>
    <ListaProductos productos={productos} onAgregar={agregar} />
    <Carrito items={carrito} onQuitar={quitar} onCobrar={cobrar} />
  </>
);

6. Librerías de componentes: qué es Mantine

La etapa dibuja botones, campos y tarjetas con HTML y CSS propios, para que se vean los fundamentos. En un sistema real, cada pantalla necesita además tablas con orden y paginación, ventanas modales, avisos, selectores de fecha, formularios con validación, menús y diseño para celular. Escribir todo eso bien (accesible con teclado, con buen contraste, igual en todos los navegadores) lleva meses. Una librería de componentes los trae hechos y probados.

Mantine es una librería de componentes para React escrita en TypeScript. Trae más de cien componentes (Button, TextInput, NumberInput, Table, Modal, AppShell para el esqueleto con barra lateral), un paquete de formularios (@mantine/form), otro de avisos emergentes (@mantine/notifications) y ganchos útiles como useDisclosure para abrir y cerrar paneles. Todo se ajusta desde un tema central (colores, tipografía, bordes), que es lo que permite cambiar el aspecto de todo el sistema sin tocar cada pantalla.

La misma tarjeta de producto, escrita con componentes de Mantine (ilustrativo: la etapa no instala Mantine):

import { Button, Card, Group, NumberInput, Text } from "@mantine/core";

export function TarjetaProducto({ producto, onAgregar }: Props) {
  const [cantidad, setCantidad] = useState<string | number>(0.25);

  return (
    <Card withBorder radius="md" padding="sm">
      <Text fw={600}>{producto.nombre}</Text>
      <Text c="dimmed" size="sm">Stock: {producto.stock}</Text>
      <Group mt="xs">
        <NumberInput value={cantidad} onChange={setCantidad} min={0} decimalScale={3} />
        <Button onClick={() => onAgregar(producto, String(cantidad))}>Agregar</Button>
      </Group>
    </Card>
  );
}

Lo que aprendiste en este módulo no cambia con Mantine. Componentes, props, estado, efectos y carpetas por funcionalidad funcionan igual: Mantine solo reemplaza los <button> y <input> propios por componentes más completos.

7. Errores comunes

Modificar el estado en lugar de reemplazarlo.

carrito.push(item); setCarrito(carrito) no actualiza la pantalla: React recibe el mismo arreglo y supone que nada cambió. Se crea uno nuevo con [...carrito, item], y para quitar se usa filter.

Guardar en el estado algo que se puede calcular.

Un useState para el total obliga a actualizarlo cada vez que cambia el carrito, y tarde o temprano queda desfasado. Lo que se deriva de otro estado se calcula al dibujar.

Olvidar la key, o usar el índice como key.

React avisa en la consola cuando falta. El índice (key={i}) parece funcionar, pero si la lista se reordena o se filtra, el estado local queda en el elemento equivocado. Se usa un identificador estable, como producto.id.

Pedir datos al dibujar, sin useEffect.

Si cargarProductos().then(setProductos) está en el cuerpo del componente, cada dibujo pide datos, cada respuesta cambia el estado y cada cambio provoca otro dibujo: un ciclo infinito de peticiones.

Sorprenderse de que el efecto se ejecute dos veces.

En desarrollo, StrictMode monta, desmonta y vuelve a montar cada componente para detectar efectos mal escritos, y por eso los productos se piden dos veces. En la versión de producción no pasa.

Esperar que Vite frene por un error de tipos.

npm run dev borra los tipos sin verificarlos, como Node en el módulo 07. Los errores aparecen en el editor y en npm run build, que ejecuta tsc antes de empaquetar.

8. Ejercicios

1. Agregá un campo de búsqueda arriba de la lista que filtre los productos por nombre. ¿En qué componente vive el texto buscado? ¿La lista filtrada es estado?

Ver respuesta

El texto vive en PantallaVentas con useState(""), porque es quien le pasa los productos a la lista. La lista filtrada no es estado: se deriva al dibujar, con productos.filter((p) => p.nombre.toLowerCase().includes(busqueda.toLowerCase())).

2. Hacé que el carrito muestre la cantidad de líneas en su título, por ejemplo «Carrito (2)». ¿Hace falta un estado nuevo?

Ver respuesta

No. Es items.length, que Carrito ya recibe por props: <h2>Carrito ({items.length})</h2>.

3. En agregar, cambiá setCarrito((anterior) => [...]) por carrito.push({ producto, cantidad }); setCarrito(carrito);. ¿Qué pasa al tocar Agregar?

Ver respuesta

El carrito no se actualiza en pantalla. El arreglo cambió por dentro, pero es el mismo objeto, y React no vuelve a dibujar. Al tocar otra cosa que sí provoque un dibujo, aparecen de golpe las líneas acumuladas.

4. Con npm run dev abierto, cambiá el texto «Todavía no hay productos.» y guardá. ¿Se recargó la página? ¿Qué pasa si cambiás una prop obligatoria en ListaProductos y ejecutás npm run build?

Ver respuesta

No se recarga: HMR reemplaza el módulo y conserva el estado. En el segundo caso, npm run dev puede seguir funcionando (o fallar en el navegador), pero npm run build se detiene con el error de tipos de tsc.
