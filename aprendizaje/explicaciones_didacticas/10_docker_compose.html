Docker Compose: todo el sistema con un comando

Cómo se empaqueta cada pieza en una imagen, cómo Compose las levanta juntas en una red propia y qué cambia respecto de ejecutarlas a mano.

1. Problema

Para ver la etapa 09 funcionando hizo falta arrancar el contenedor de MariaDB, activar el entorno virtual, aplicar las migraciones, cargar los datos, levantar el backend en una terminal y el frontend en otra, cada uno con su puerto y su configuración. En el servidor de la facultad habría que repetir todo eso, instalar Python y Node en las versiones correctas y asegurarse de que los procesos se reinicien si el servidor se apaga.

Docker empaqueta cada pieza en una imagen que trae todo lo que necesita. Docker Compose describe en un archivo cómo se combinan esas piezas. Con eso, el sistema completo se levanta igual en cualquier máquina con Docker, con un solo comando: docker compose up -d --build.

2. Concepto

2.1 Imagen, contenedor y Dockerfile

Una imagen es un paquete de solo lectura con un sistema de archivos mínimo, un programa y sus dependencias. Un contenedor es una imagen en ejecución, con su propia red y sus propios procesos. Se pueden crear muchos contenedores de la misma imagen, y borrar un contenedor no borra la imagen.

Un Dockerfile es la receta para construir una imagen. Cada instrucción agrega una capa: FROM elige la imagen base, WORKDIR fija la carpeta de trabajo, COPY copia archivos del contexto (la carpeta que se le pasa a Docker), RUN ejecuta un comando al construir y CMD define qué se ejecuta al arrancar el contenedor.

Docker guarda cada capa y la reutiliza mientras no cambie lo que la produjo. Por eso api.Dockerfile copia primero requirements.txt e instala las dependencias, y recién después copia el código. Si se modifica un router, Docker reutiliza la capa de dependencias y la reconstrucción tarda segundos en lugar de minutos.

2.2 Construcción en dos etapas

El frontend necesita Node para construirse, pero no para servirse: en producción son archivos estáticos. web.Dockerfile usa dos etapas. La primera parte de node:24-alpine, instala las dependencias con npm ci (que respeta exactamente package-lock.json) y ejecuta npm run build. La segunda parte de nginx y copia de la primera solo la carpeta dist/. La imagen final pesa 93 MB y no contiene Node ni el código fuente.

2.3 compose.yaml

El archivo de Compose declara servicios, y cada servicio se convierte en un contenedor. La Tabla 1 resume los tres de la etapa.

ports: "8081:80" publica el puerto 80 del contenedor en el 8081 de la PC. environment pasa variables de entorno, y ${VARIABLE} toma su valor del archivo .env. depends_on ordena el arranque, y con condition: service_healthy el backend espera a que la base responda, no solo a que su contenedor haya arrancado. Para saber si responde, el servicio db declara un healthcheck: un comando que Docker ejecuta cada 5 segundos.

2.4 La red: cada servicio se llama por su nombre

Compose crea una red privada (punto-lacteo_default) y conecta los tres contenedores. Dentro de esa red, el nombre de cada servicio funciona como dirección. Este es el cambio más importante respecto de los módulos anteriores: dentro de un contenedor, 127.0.0.1 es ese mismo contenedor, no la PC. Por eso el backend se conecta a db:3306 y nginx reenvía a http://api:8000.

Como la base no tiene ports, nadie fuera de la red puede conectarse a ella. Solo el servicio web queda expuesto, y todo lo demás pasa por él.

2.5 Volúmenes: los datos fuera del contenedor

Un contenedor es descartable: docker compose down lo borra, y una actualización lo reemplaza por uno nuevo. Los datos de MariaDB no pueden vivir adentro. El volumen datos es un almacenamiento que administra Docker y que se monta en /var/lib/mysql. Sobrevive a down y a las reconstrucciones. Solo se borra con docker compose down -v o docker volume rm, y por eso ese comando se usa con cuidado.

2.6 Configuración y secretos

Las contraseñas de la base y la CLAVE_SECRETA no están en compose.yaml: están en .env, que git ignora. El repositorio incluye .env.ejemplo con los nombres de las variables y valores de relleno. En el servidor se crea un .env propio con valores reales. Así el mismo compose.yaml sirve para la PC y para el servidor.

2.7 nginx: el proxy de producción

nginx es un servidor web que hace dos trabajos en la etapa: entrega los archivos de dist/ y funciona como proxy inverso para /api. Es el reemplazo del proxy de Vite del módulo 09, con la misma regla: /api/productos se reenvía a http://api:8000/productos. Por eso el frontend no cambió nada para funcionar en producción. En un despliegue público, este mismo nginx (u otro delante, como el swag que usa la materia IoT) es donde se agrega HTTPS con un certificado.

2.8 Qué pasa en cada arranque

El CMD del backend ejecuta tres comandos encadenados: alembic upgrade head, python -m app.semilla y fastapi run. En el primer arranque, Alembic crea las tablas y la semilla carga usuarios y productos. En los siguientes, Alembic ve que la base ya está en la última versión, la semilla ve que ya hay datos, y ninguno hace nada. Cuando el proyecto real agregue una migración, desplegarla será reconstruir y reiniciar: la migración se aplica sola.

3. Código mínimo

El servicio del backend en compose.yaml:

api:
  build:
    context: ../06_seguridad
    dockerfile: ../10_docker_compose/api.Dockerfile
  environment:
    DATABASE_URL: mariadb+pymysql://${DB_USER}:${DB_PASSWORD}@db:3306/punto_lacteo?charset=utf8mb4
    CLAVE_SECRETA: ${CLAVE_SECRETA}
  depends_on:
    db:
      condition: service_healthy

La receta del backend, con las dependencias antes que el código para aprovechar la caché:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["sh", "-c", "alembic upgrade head && python -m app.semilla && fastapi run app/main.py --host 0.0.0.0 --port 8000"]

El reenvío de la API en nginx.conf:

location /api/ {
    proxy_pass http://api:8000/;     # la barra final quita el prefijo /api
}

Desde la carpeta de la etapa:

docker compose up -d --build    # construye y levanta todo; después, http://localhost:8081
docker compose logs -f api      # registros del backend en vivo
docker compose down             # detiene todo (los datos quedan en el volumen)

Faltan tres cosas que este material no cubre: HTTPS con un certificado, copias de seguridad periódicas del volumen (por ejemplo, con mariadb-dump) y que Docker reinicie los servicios si el servidor se reinicia (restart: unless-stopped en cada servicio).

6. Errores comunes

Usar 127.0.0.1 o localhost entre contenedores.

Dentro del contenedor api, 127.0.0.1 es el propio contenedor, donde no hay ningún MariaDB. La conexión falla con «Connection refused». Entre servicios se usa el nombre del servicio: db.

Copiar node_modules de Windows a la imagen.

Algunas dependencias traen programas compilados para el sistema operativo donde se instalaron, y los de Windows no funcionan en el Linux del contenedor. web.Dockerfile.dockerignore lo excluye, y la imagen instala todo de nuevo con npm ci.

Ejecutar docker compose down -v sin pensar.

La opción -v borra el volumen y, con él, todas las ventas. Para detener el sistema alcanza con down.

Confiar en depends_on sin healthcheck.

Sin la condición service_healthy, el backend arranca apenas arranca el contenedor de la base, que todavía tarda unos segundos en aceptar conexiones. Alembic falla y el backend se detiene.

Escuchar en 127.0.0.1 dentro del contenedor.

Un servidor que escucha en 127.0.0.1 solo acepta conexiones del propio contenedor, y nginx no llega. Dentro de un contenedor se escucha en 0.0.0.0: por eso el CMD usa --host 0.0.0.0.

Subir el .env al repositorio.

Tiene las contraseñas y la clave que firma los tokens. Se sube .env.ejemplo, con los nombres y valores de relleno.

7. Ejercicios

1. Cambiá un texto de Carrito.tsx en la etapa 09 y ejecutá docker compose up -d --build. ¿Qué imágenes se reconstruyen? ¿Qué capas se reutilizan?

Ver respuesta

Solo se reconstruye web, porque el contexto de api no cambió. Dentro de web, la capa de npm ci se reutiliza (aparece como CACHED), porque package.json y package-lock.json no cambiaron. Se repiten COPY . . y npm run build.

2. Registrá una venta, ejecutá docker compose down y después up -d. ¿Sigue la venta? ¿Qué muestra docker compose logs api sobre las migraciones?

Ver respuesta

Sí: la venta está en el volumen. Los registros no muestran ningún «Running upgrade», porque la base ya está en la migración 0002, y la semilla solo informa «Datos iniciales listos.» sin cargar nada.

3. Abrí una consola SQL dentro del contenedor de la base con docker compose exec db mariadb -u pl -p punto_lacteo y contá las ventas. ¿Por qué funciona si la base no publica ningún puerto?

Ver respuesta

exec ejecuta el cliente mariadb dentro del mismo contenedor que el servidor, así que se conecta localmente, sin pasar por la red. Publicar un puerto solo hace falta para conectarse desde afuera de Docker.

4. Agregá restart: unless-stopped a los tres servicios. ¿Qué pasa si reiniciás Docker Desktop? ¿Por qué importa en el servidor de la facultad?

Ver respuesta

Al volver Docker, los contenedores arrancan solos, salvo que se hayan detenido a mano con docker compose stop o down. En el servidor, eso significa que un corte de luz o un reinicio no deja el sistema apagado hasta que alguien lo note.
