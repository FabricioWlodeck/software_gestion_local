Frontend ↔ backend: la pantalla habla con la API

Cómo React pide y envía datos con fetch, por qué el navegador bloquea algunas peticiones (CORS), cómo se maneja el inicio de sesión y qué hace la pantalla con cada respuesta.

1. Problema

La pantalla de la etapa 08 funciona con datos de prueba, y la API de la etapa 06 funciona desde /docs. Falta unirlas, y al hacerlo aparecen problemas que no estaban en ninguna de las dos por separado. El navegador tiene reglas de seguridad propias y bloquea peticiones que curl deja pasar. El token hay que guardarlo en algún lado y enviarlo en cada petición. Y cada petición puede tardar, fallar por la red o volver con un 401, un 409 o un 422, y la cajera tiene que ver algo razonable en cada caso.

2. Concepto

2.1 fetch

fetch es la función del navegador para enviar peticiones HTTP. Devuelve una promesa, así que se usa con await, y el resultado es un objeto Response con el código (status), un indicador de éxito (ok, verdadero para los códigos 2xx) y métodos para leer el cuerpo, como json().

fetch no lanza un error por un 404 o un 409: para fetch, el servidor respondió y la petición salió bien. Solo lanza un error si no hubo respuesta (sin red, servidor apagado o bloqueo del navegador). Por eso hay que mirar respuesta.ok después de cada petición.

2.2 Un solo lugar para hablar con la API

Si cada pantalla llamara a fetch por su cuenta, cada una tendría que acordarse de la URL base, de agregar el token, de interpretar los errores de FastAPI y de reaccionar a un 401. La etapa concentra todo eso en src/api/cliente.ts. Su función pedir agrega el header Authorization, revisa respuesta.ok, convierte el detail de FastAPI en un mensaje legible y lanza un ErrorApi con el código. Las pantallas solo llaman a api.listarProductos() o api.registrarVenta(items). Es la misma idea que los repositorios del backend: una capa que esconde los detalles de cómo se obtienen los datos.

2.3 Mismo origen y CORS

El origen de una página es la combinación de protocolo, servidor y puerto: http://localhost:5173 y http://127.0.0.1:8000 son orígenes distintos. Por seguridad, el navegador no deja que una página lea respuestas de otro origen. Si no existiera esa regla, cualquier sitio que se abriera en el navegador de la dueña podría hacer peticiones a la API de Punto Lácteo con sus credenciales y leer las ventas.

El servidor puede autorizar otros orígenes con CORS (Cross-Origin Resource Sharing o Intercambio de Recursos de Origen Cruzado), respondiendo headers como Access-Control-Allow-Origin. Antes de una petición con Authorization o con JSON, el navegador envía una petición de verificación previa (preflight): un OPTIONS que pregunta si está permitido. La etapa 06 no configura CORS, así que, desde la página de la caja, un fetch directo a 127.0.0.1:8000 falla. Este es el mensaje real del navegador: 

Access to fetch at 'http://127.0.0.1:8000/productos' from origin 'http://localhost:5173' has been blocked by CORS policy: Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on the requested resource.

CORS es una protección del navegador: curl, cliente.py y /docs no la aplican, y por eso la misma API funcionaba en los módulos anteriores.

2.4 La solución: un proxy, mismo origen

Hay dos formas de resolverlo. Una es agregar CORSMiddleware en FastAPI con la lista de orígenes permitidos. La otra, que usa la etapa, es que el navegador nunca hable con otro origen. En desarrollo, el servidor de Vite funciona como proxy: el frontend pide /api/productos a localhost:5173, y Vite reenvía la petición a 127.0.0.1:8000/productos. Para el navegador todo viene del mismo origen. En producción, nginx hace exactamente lo mismo (módulo 10), y por eso el código del frontend no cambia entre desarrollo y producción.

2.5 La sesión en el frontend

El inicio de sesión sigue cuatro pasos. Primero, el formulario envía usuario y contraseña a POST /api/auth/token como formulario (URLSearchParams), como exige OAuth2. Segundo, el token recibido se guarda en localStorage, que conserva datos en el navegador aunque se cierre la pestaña. Tercero, se pide GET /api/auth/yo para saber nombre y rol. Cuarto, desde ahí, cada petición lleva el token en el header. Al abrir la página, si quedó un token guardado, se repite el tercer paso para comprobar que siga siendo válido. Si cualquier petición responde 401, el cliente borra el token y la aplicación vuelve al inicio de sesión.

2.6 Contexto: datos para todo el árbol

Casi todas las pantallas necesitan saber quién inició sesión. Pasar el usuario por props de padre a hijo a nieto llenaría de props componentes que no lo usan. React ofrece el contexto: createContext crea un canal, un Provider en lo alto del árbol pone un valor, y cualquier componente de abajo lo lee con useContext. La etapa lo envuelve en un gancho propio, useSesion(), que devuelve el usuario y las funciones para iniciar y cerrar sesión.

2.7 Los tres estados de una petición

Cada dato que viene del backend pasa por tres estados, y la pantalla tiene que contemplar los tres. Mientras carga, se muestra «Cargando productos…». Si sale bien, se muestran los datos. Si hay un error, se muestra el mensaje del backend. Al cobrar, un 409 o un 422 no vacían el carrito: la cajera corrige la cantidad y vuelve a intentar. Después de una venta exitosa, la pantalla vuelve a pedir los productos, porque el stock cambió.

2.8 La interfaz según el rol

App muestra el resumen de ventas solo si usuario.rol === "duenio". Eso es experiencia de uso, no seguridad: el código del frontend está en el navegador del empleado, y cualquiera puede modificarlo o enviar la petición a mano. La protección real es el 403 del backend (módulo 06).

3. Código mínimo

La función que hacen todas las peticiones, en src/api/cliente.ts (resumida):

async function pedir<T>(ruta: string, opciones: RequestInit = {}): Promise<T> {
  const headers = new Headers(opciones.headers);
  const token = leerToken();
  if (token) headers.set("Authorization", `Bearer ${token}`);

  const respuesta = await fetch(`/api${ruta}`, { ...opciones, headers });
  if (!respuesta.ok) {                        // fetch no lanza error por un 4xx: hay que mirarlo
    const cuerpo = await respuesta.json().catch(() => null);
    if (respuesta.status === 401 && token) { borrarToken(); alPerderSesion(); }
    throw new ErrorApi(respuesta.status, mensajeDeError(cuerpo, respuesta.status));
  }
  return (await respuesta.json()) as T;
}

El proxy de desarrollo en vite.config.ts:

server: {
  proxy: {
    '/api': {
      target: 'http://127.0.0.1:8000',
      rewrite: (ruta) => ruta.replace(/^\/api/, ''),   // /api/productos → /productos
    },
  },
},

Una pantalla que usa la API y la sesión:

const { usuario } = useSesion();

async function cobrar() {
  try {
    const venta = await api.registrarVenta(items);
    setMensaje(`Venta ${venta.id} registrada. Total: ${formatearPrecio(venta.total)}`);
  } catch (problema) {
    setError(problema instanceof ErrorApi ? problema.message : "No se pudo conectar con el servidor");
  }
}

Se ejecuta con el backend de la etapa 06 y el frontend en dos terminales:

fastapi dev app/main.py   # en etapas/06_seguridad, puerto 8000
npm run dev               # en etapas/09_front_back, puerto 5173

6. Errores comunes

Suponer que fetch lanza un error con un 404 o un 409.

No lo hace: la promesa se resuelve con la respuesta, y si no se mira respuesta.ok, el código intenta usar el cuerpo de un error como si fueran datos. cliente.ts lo revisa en un solo lugar.

Pensar que la API está rota porque falla en el navegador y funciona con curl.

Es CORS: la API responde, pero el navegador no deja que la página lea la respuesta. La consola del navegador lo dice explícitamente. Se resuelve con el proxy o con CORSMiddleware, nunca desactivando la seguridad del navegador.

Escribir http://127.0.0.1:8000 dentro de los componentes.

Esa dirección no existe en el navegador de la cajera cuando el sistema está en el servidor. Con rutas relativas (/api/...) y un proxy, el mismo código funciona en desarrollo y en producción.

Olvidar Content-Type: application/json al enviar JSON.

Sin ese header, FastAPI no interpreta el cuerpo como JSON y responde 422. api.registrarVenta lo agrega.

Escribir useEffect(async () => {...}).

Una función async devuelve una promesa, y useEffect espera que el efecto devuelva nada o una función de limpieza. Se escribe una función común que adentro llama a la asíncrona, o se usa .then(), como en la etapa.

Vaciar el formulario cuando el backend rechaza.

Si un 409 vacía el carrito, la cajera tiene que cargar todo de nuevo para corregir una cantidad. Ante un error, el estado queda como estaba y se muestra el mensaje.

7. Ejercicios

1. Comentá el bloque proxy de vite.config.ts y cambiá BASE en cliente.ts por "http://127.0.0.1:8000". ¿Qué muestra la consola del navegador? ¿Qué habría que agregar en el backend para que funcione así?

Ver respuesta

El error de CORS de la sección 2.3. En la etapa 06 habría que agregar el middleware en main.py (y después volver todo a como estaba):

from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_methods=["*"],
    allow_headers=["*"],
)

2. Deshabilitá el botón Cobrar mientras se envía la venta, para que un doble clic no registre dos ventas. ¿Qué estado nuevo hace falta y dónde vive?

Ver respuesta

Un const [enviando, setEnviando] = useState(false) en PantallaVentas, que se pone en true al empezar cobrar y en false en un finally. Se pasa a Carrito como prop, y el botón usa disabled={enviando}. Recordá el módulo 01: POST no es idempotente.

3. Cuando el token vence, la aplicación vuelve al inicio de sesión sin explicar por qué. Hacé que muestre «Tu sesión venció, volvé a ingresar».

Ver respuesta

En SesionProvider, el callback de cuandoSePierdaLaSesion puede guardar un mensaje en un estado nuevo (por ejemplo, aviso) además de borrar el usuario. Ese aviso se agrega al contexto, y PantallaLogin lo muestra arriba del formulario.

4. ¿Por qué api.iniciarSesion envía URLSearchParams y api.registrarVenta envía JSON.stringify? ¿Qué pasaría si se intercambiaran?

Ver respuesta

Porque cada ruta espera un formato distinto: /auth/token sigue OAuth2, que exige un formulario, y /ventas recibe un schema de Pydantic en JSON. Intercambiados, las dos responderían 422: FastAPI no encontraría los campos donde los espera.
