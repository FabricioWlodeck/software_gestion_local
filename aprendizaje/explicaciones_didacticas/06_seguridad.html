Seguridad: contraseñas, tokens y roles

Cómo se guardan las contraseñas, cómo el servidor sabe quién hace cada petición, qué puede hacer cada rol y en qué se diferencian hash, cifrado y firma.

1. Problema

En la etapa 05, la caja envía "usuario_id": 2 y el servidor le cree. Cualquiera que conozca la API puede registrar ventas a nombre de otra persona, ver las métricas del negocio o borrar productos con el token fijo que está escrito en el código. El sistema real exige lo contrario: que la dueña vea todo, que un empleado pueda cobrar pero no ver las ganancias, y que quede registro de quién hizo cada cosa.

Para eso hacen falta tres piezas. La primera son contraseñas guardadas de forma que ni quien robe la base pueda leerlas. La segunda es una manera de que, después de iniciar sesión, cada petición demuestre quién la hace sin enviar la contraseña de nuevo. La tercera son reglas que digan qué puede hacer cada rol.

2. Concepto

2.1 Hash, cifrado y firma: tres herramientas distintas

En el uso cotidiano, todo esto se llama «encriptar», pero son tres operaciones con propósitos distintos (Tabla 1), y confundirlas lleva a errores graves.

OperaciónQué hace¿Se puede revertir?¿Usa clave?Uso en Punto Lácteo
HashConvierte un texto en una huella de largo fijo. La misma entrada da siempre una huella verificable.NoNo (usa una sal aleatoria)Guardar contraseñas (Argon2)
CifradoTransforma un texto para que solo lo lea quien tenga la clave.Sí, con la claveSíProteger los datos en tránsito (HTTPS)
FirmaAgrega a un mensaje un sello que prueba quién lo emitió y que nadie lo modificó. El mensaje sigue legible.No hace falta: no oculta nadaSíTokens de sesión (JWT con HMAC-SHA256)

2.2 Contraseñas: se guarda el hash, nunca la contraseña

La base nunca guarda bruno123. Guarda el resultado de pasarla por una función de hash. Al iniciar sesión, el servidor calcula el hash de lo que escribió el usuario con los mismos parámetros y compara. Si alguien roba la base, obtiene hashes, y de un hash no se puede volver a la contraseña.

Lo que sí puede hacer un atacante es probar contraseñas posibles hasta encontrar una que dé el mismo hash. Por eso no se usan funciones rápidas como SHA-256: una placa de video calcula miles de millones por segundo. Se usa Argon2, diseñada para ser lenta y consumir memoria a propósito. Un hash de la etapa se ve así: 

$argon2id$v=19$m=65536,t=3,p=4$SMxRB3HHgFEyJ7AJ4bp2dw$N4pijPt6b57bq4PCreyJDD8KCLHLOGebOqw5KSgBpe0

El texto guarda todo lo necesario para verificar: el algoritmo (argon2id), la versión, el costo (m=65536 KiB de memoria, t=3 pasadas y p=4 hilos), la sal y el hash. La sal es un valor aleatorio distinto para cada contraseña. Por eso la misma contraseña da hashes distintos cada vez (explorar_seguridad.py lo muestra), y un atacante no puede usar tablas precalculadas de hashes de contraseñas comunes.

2.3 Autenticación y autorización

La autenticación responde «¿quién sos?» y su fracaso es un 401. La autorización responde «¿podés hacer esto?» y su fracaso es un 403. Bruno, con un token válido, está autenticado. Cuando intenta ver las ventas, no está autorizado.

2.4 Inicio de sesión con OAuth2

La etapa sigue el flujo de contraseña de OAuth2 (Open Authorization 2.0 o Autorización Abierta 2.0), que es el que muestra la documentación de FastAPI. El cliente envía usuario y contraseña una sola vez a POST /auth/token, como formulario (username=...&password=...). Si son correctos, el servidor responde con un token: {"access_token": "eyJ...", "token_type": "bearer"}. A partir de ahí, cada petición lleva el header Authorization: Bearer <token>, y la contraseña no vuelve a viajar.

Bearer significa «portador»: quien porta el token, pasa. HTTP no tiene memoria (módulo 01), así que el token viaja en cada petición. En FastAPI, OAuth2PasswordBearer(tokenUrl="auth/token") es una dependencia que lee ese header y le indica a /docs dónde iniciar sesión: por eso aparece el botón Authorize.

2.5 JWT: un token que se verifica sin consultar nada

El token es un JWT (JSON Web Token o Token Web JSON): tres partes separadas por puntos. El encabezado dice qué algoritmo se usó. El contenido (payload) trae los datos, llamados claims: sub (el id del usuario), rol, iat (cuándo se emitió) y exp (cuándo vence). La firma es un HMAC-SHA256 (Hash-based Message Authentication Code o Código de Autenticación de Mensajes basado en Hash) del encabezado y el contenido, calculado con la CLAVE_SECRETA del servidor.

Las dos primeras partes están en Base64URL, una codificación, no un cifrado: cualquiera puede leerlas. Lo que nadie puede hacer sin la clave es modificarlas y calcular una firma válida. Por eso el servidor confía en el contenido sin guardar las sesiones en ningún lado. La contracara es que un token no se puede anular antes de que venza; por eso dura un turno (8 horas) y no semanas. La etapa, además, busca al usuario en la base en cada petición y usa el rol guardado ahí: si la dueña le quita un permiso a alguien, vale desde la petición siguiente.

2.6 Dónde guarda el token el frontend

El material guarda el token en localStorage (módulo 09), como hace la documentación oficial. Tiene un riesgo: si un atacante logra ejecutar JavaScript en la página, mediante un ataque XSS (Cross-Site Scripting o Secuencia de Comandos en Sitios Cruzados), puede leerlo. La alternativa es una cookie httpOnly, que JavaScript no puede leer y el navegador envía sola. Esa cookie protege contra XSS, pero exige defenderse de otro ataque, CSRF (Cross-Site Request Forgery o Falsificación de Peticiones en Sitios Cruzados). Para el proyecto real conviene evaluarla; para aprender, el header Authorization deja ver todo el mecanismo.

2.7 HTTPS: cifrado en tránsito

En las etapas, las peticiones viajan sin cifrar por 127.0.0.1, dentro de la misma PC. En el servidor de la facultad, la contraseña del formulario y el token cruzarían la red a la vista de cualquiera que la escuche. HTTPS cifra cada mensaje con TLS (Transport Layer Security o Seguridad de la Capa de Transporte). Lo habitual es que un proxy inverso (como nginx) atienda HTTPS con un certificado y le pase las peticiones a Uvicorn. Sin HTTPS, nada de este módulo protege de verdad.

2.8 Roles

Los permisos se asignan por rol: RBAC (Role-Based Access Control o Control de Acceso Basado en Roles). La etapa tiene dos roles fijos, duenio y empleado. La dependencia requerir_rol es una fábrica: requerir_rol("duenio") devuelve una función que FastAPI ejecuta antes de la ruta y que responde 403 si el rol no coincide. Cada ruta declara en su firma quién puede usarla (Tabla 2).

2.9 Secretos

CLAVE_SECRETA es el dato más sensible del backend: quien la conozca puede fabricar un token de la dueña. Se genera al azar (secrets.token_hex(32)), se pasa por variable de entorno y nunca se sube a git. Lo mismo vale para la contraseña de la base. El módulo 10 los reúne en un archivo .env.

3. Código mínimo

Hash y token en app/seguridad.py, sin HTTP ni base de datos:

hasheador = PasswordHash.recommended()   # Argon2

def hashear(contrasena: str) -> str:
    return hasheador.hash(contrasena)

def crear_token(usuario_id: int, rol: str) -> str:
    ahora = datetime.now(UTC)
    contenido = {"sub": str(usuario_id), "rol": rol, "iat": ahora,
                 "exp": ahora + timedelta(minutes=MINUTOS_DE_SESION)}
    return jwt.encode(contenido, CLAVE_SECRETA, algorithm=ALGORITMO_JWT)

Las dos guardias en app/dependencies.py:

esquema_oauth2 = OAuth2PasswordBearer(tokenUrl="auth/token")

def obtener_usuario_actual(token: Annotated[str, Depends(esquema_oauth2)], sesion: SesionDep) -> Usuario:
    try:
        contenido = leer_token(token)          # verifica firma y vencimiento
    except jwt.InvalidTokenError:
        raise no_autenticado                   # 401
    ...

def requerir_rol(*roles: str):
    def verificar_rol(usuario: UsuarioActualDep) -> Usuario:
        if usuario.rol not in roles:
            raise HTTPException(status_code=403, detail="No tenés permiso para esta acción")
        return usuario
    return verificar_rol

Cada ruta declara quién puede usarla. La venta queda a nombre del usuario del token:

Ocultar no es proteger. En el módulo 09, la pantalla de un empleado no muestra el botón para ver las ventas. Eso mejora la experiencia, pero la protección real es el 403 de esta etapa: cualquiera puede enviar la petición sin usar la pantalla.

6. Errores comunes

Guardar contraseñas en texto plano o con MD5 o SHA-256.

Texto plano expone todas las contraseñas con un solo robo. MD5 y SHA-256 son tan rápidos que se prueban miles de millones de contraseñas por segundo. Se usa una función lenta con sal, como Argon2.

Decir qué falló en el inicio de sesión.

Responder «el usuario no existe» o «la contraseña es incorrecta» le dice a un atacante qué nombres existen. La etapa responde lo mismo en los dos casos, y además tarda lo mismo: si el usuario no existe, verifica contra un hash ficticio.

Poner datos secretos en el JWT.

El contenido se lee con un decodificador de Base64. Nunca lleva contraseñas, ni datos que el usuario no deba ver.

Confiar en el rol que viene en el token sin mirar la base.

Si la dueña degrada a un usuario, su token sigue diciendo el rol viejo hasta que venza. La etapa usa el rol de la base, que se consulta en cada petición.

Subir la CLAVE_SECRETA a git.

Un repositorio se copia, se comparte y se publica. Quien tenga la clave puede fabricar tokens de cualquier usuario. Si se filtra, se cambia, y todos vuelven a iniciar sesión.

Desplegar sin HTTPS.

La contraseña del formulario y el token viajan legibles por la red. Hash, firma y roles no sirven si el token se puede copiar en tránsito.

7. Ejercicios

1. Ejecutá python explorar_seguridad.py dos veces. ¿Qué cambia entre una ejecución y otra en los hashes y en el token? ¿Por qué el token cambia aunque el usuario sea el mismo?

Ver respuesta

Los hashes cambian por la sal aleatoria. El token cambia porque iat y exp dependen del momento en que se crea, y cualquier cambio en el contenido cambia la firma.

2. Arrancá el servidor con $env:MINUTOS_DE_SESION = "1", iniciá sesión, esperá dos minutos y hacé una petición con ese token. ¿Qué responde? ¿Qué línea lo decide?

Ver respuesta

Responde 401 «Token inválido o vencido». jwt.decode, dentro de leer_token, compara exp con la hora actual y lanza ExpiredSignatureError, que es una subclase de InvalidTokenError.

3. Agregá GET /ventas/mias, para que cada empleado vea solo sus propias ventas. ¿Qué guardia usás y qué cambia en el repositorio?

Ver respuesta

Se usa UsuarioActualDep (cualquiera identificado) y se pasa usuario.id al service. El repositorio agrega un método que filtra con .where(Venta.usuario_id == usuario_id). La ruta se declara antes de cualquier ruta con {venta_id}, por el orden de rutas que se vio en el módulo 02.

4. ¿Por qué POST /auth/token recibe un formulario y no JSON?

Ver respuesta

Porque el flujo de contraseña de OAuth2 define que usuario y contraseña se envían como formulario, con los campos username y password. Respetar el estándar permite que herramientas como el botón Authorize de /docs funcionen sin configuración.

5. Iniciá sesión, reiniciá el servidor con otra CLAVE_SECRETA y usá el token viejo. ¿Qué pasa? ¿En qué situación real conviene hacer esto a propósito?

Ver respuesta

Responde 401: la firma del token no coincide con la clave nueva. Se hace a propósito cuando la clave se filtró o cuando hay que cerrar todas las sesiones a la vez, por ejemplo al despedir a alguien que tenía un token vigente.
